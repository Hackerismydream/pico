# 05 记忆系统：协议、双轨、fail-closed

## 一、问题：上周说过的话，这周还认不认

场景放具体。用户上周在会话里说过「我们项目用 uv，别给我推荐 pip」。这周开了个新会话，agent 张口就是 `pip install`。用户的信任从这一刻开始掉，而且这类翻车没有报错、没有日志，只有用户心里那句「它根本不记得我」。

第 03 章的机制帮不上忙：working state 和 archive 都活在单个会话里，会话结束就到头了。跨会话的长期记忆是另一个问题，而且朴素做法一个比一个坑：

1. 把所有历史都带上。第 03 章已经算过这笔账，窗口装不下，成本也不允许。
2. 让模型自己往一个大文件里记笔记。没有失效机制、没有检索、越滚越大；更糟的是文件内容会被原样拼进 prompt，一段被投毒的「笔记」从此每轮都在指挥模型。
3. 挂个向量库，把一切都 embed 进去。语义检索是强了，但三个新问题跟着来：召回不可解释（为什么是这条？），所有权混乱（用户的偏好和 agent 自己学到的操作技能混在一坨），以及最隐蔽的一条：库挂了怎么办？多数实现选择静默降级，当作没有记忆继续跑。用户以为它记得，它其实什么都没存。

主流方案大致两个流派：文件型（Claude Code 的 CLAUDE.md 一族，人可读可编辑，但没有语义检索）和向量库型（mem0、MemOS 这类，检索强但黑盒）。Pico 的答案是两者的混合，外加两条自己的立场：记忆按所有者分轨，故障一律显式。

## 二、三层记忆的分工

先把全景图放正，三层各管一段寿命：

| 层 | 活多久 | 归谁管 | 章节 |
|---|---|---|---|
| working state（目标/线索/决策） | 一个会话 | Curator，第 6 段 | 03 |
| archive（被移出窗口的原文） | 一个会话，可取回 | CuratorArchiveStore | 03 |
| 长期记忆 | 跨会话 | 本章：宿主文件面 + MemoryBackend 插件 | 05 |

长期记忆又分两半。宿主文件面是慢变的 markdown（`user_memory/profile/user.md`、`episodic/episodes.md` 等），人可读可改；语义召回走 MemoryBackend 协议，由插件实现（默认 EverOS）。两半在 prompt 的第 3 段合流成一个 `# Memory` 块，代码文件头把这个设计一句话说完了：Two contributing sources, one owner。

## 三、协议：五个方法，一个都不多

`pico/memory_engine/backend.py` 整个文件 167 行，就是这份契约（原码）：

```python
@runtime_checkable
class MemoryBackend(Protocol):
    async def recall(
        self,
        query: str,
        *,
        user_id: str | None = None,
        agent_id: str | None = None,
        top_k: int,
    ) -> list[Memory]: ...
    async def store(self, session_id: str, messages: list[dict[str, Any]]) -> None: ...
    async def feedback(self, signals: dict[str, Any]) -> None: ...
    async def start(self) -> None: ...
    async def stop(self) -> None: ...
```

方法在文件里的排列顺序就是热路径顺序：recall 每轮上下文装配都调（可能两次，双轨各一），store 每轮之后，feedback 偶尔，start/stop 一生各一次。几条设计决定值得逐条讲：

**双轨用 XOR 表达。** recall 的 `user_id` 和 `agent_id` 恰好设一个。模块 docstring 写得明白：双轨后端（EverOS）把设了的那个字段路由到对应存储（用户轨是 episodes/profiles，agent 轨是 cases/skills）；平轨后端（docstring 点名 mem0、MemOS）只认 `user_id`，对 `agent_id` 调用返回空列表。两个都设或都不设是调用方 bug，适配器的约定是 warn 加返回空，不抛。

**metadata 是逃生舱，host 不读它。** `Memory` 载体只有 `text`、`score`、`metadata` 三个字段，而上下文装配器只把 `text` 放进 prompt。插件想塞多少结构化信息都行，但没有任何一条能绕过渲染层直接进上下文。

**feedback 允许是 no-op。** 协议明说了。EverOS 1.1.2 的服务层没有暴露技能置信度的写通道，所以适配器的 feedback 就是记一条 INFO 然后返回，代码注释把话说满：this is not dead code，主链路的管线是通的，等上游有写通道就接上。

**为什么是 Protocol 不是基类。** `runtime_checkable` 的代价是任何表面匹配的鸭子类型都算数，注释说这正是想要的：契约测试不必强迫插件作者继承什么。顺带一段历史：上一代抽象叫 MemoryEngine ABC，带一堆子系统访问器，后来整个删掉了，`base.py` 开头留了句墓志铭：The L4 indirection turned out to leak too much surface (subsystem accessors that third-party plugins couldn't satisfy)。接口面大一分，第三方实现的门槛就高一分，这是被实践教育后收窄的。

## 四、插件机制：清单声明，工厂构造

后端不是硬编码的，走插件清单。EverOS 那份 `pico-plugin.toml` 是最好的样例（节选）：

```toml
[plugin]
id                 = "everos-memory"
bundled            = true
enabled_by_default = true

[[plugin.contributes.memory_backends]]
name    = "everos"
factory = "pico.plugin.memory.everos.backend:make_backend"

[[plugin.contributes.tools]]
name    = "understand_media"
factory = "pico.plugin.memory.everos.tools:make_understand_media_tool"
```

发现有四个来源，优先级写成了 IntEnum：bundled(4) > user(3) > project(2) > entry_points(1)。方向是反直觉的：内置插件优先级最高，本地插件不能遮蔽同名内置插件。注释把理由叫 builtin shadow rule，防的是「装了个同名包，系统的记忆后端被悄悄换掉」这类供应链式意外。冲突双向打日志，谁遮蔽了谁、谁被遮蔽，都有记录。

选择后端只有一个配置键：`memory.backend = "everos"`（默认）。设成 `null` 是关闭记忆的唯一合法路径，关闭的是语义召回、持久化、个性化和 Curator 的读记忆工具，Session 和本地技能不受影响。

一处如实交代：清单里的 `config_schema` 段是描述性元数据，注册表把用户的 `plugins.config["everos-memory"]` 原样传给工厂，不做校验，字段合法性由适配器自己把关。文档把这条列在已知局限里，没装懂。

## 五、fail-closed：一条拦截链，三次事故的产物

架构不变量第 5 条：`memory.backend = null` 关闭记忆；选中的后端如果构造、启动、召回、存储任何一步失败，不允许静默消失。这句话在代码里是一条完整的拦截链：

| 阶段 | 行为 |
|---|---|
| 未选（backend=null） | 返回 None，唯一的合法关闭 |
| contribution 找不到 | 抛 PluginNotFoundError |
| 工厂 import/解析失败 | 抛 PluginFactoryImportError |
| 构造期配置非法 | 抛 ValueError |
| 启动失败 | 抛 RuntimeError，且被装配层缓存、后续调用重抛（第 00 章讲过） |
| 没 start 就 recall/store | 抛 RuntimeError("not started") |
| 召回失败 | 原样上抛，整轮装配失败（第 03 章的裸 gather） |
| store 失败 | 原样上抛，但发生在 Session 落盘之后 |

两个刻意的例外，边界画得很清楚：feedback 失败只记日志（best-effort telemetry, not load-bearing state），插件贡献的工具构造失败跳过该工具不影响启动。文档一句话概括这条非对称：A selected persistence backend must not silently lose Memory, while an optional Plugin Tool must not prevent the Agent from booting。

这套纪律不是天生的，是三次真实事故各贡献了一块：

**事故一：Windows 上的静默降级。** everos 在模块加载时 import POSIX 的 fcntl，Windows 上直接炸，早期代码把这个炸吞掉、降级成 no-op 适配器，还把日志错记成「everos 未安装」。用户在 Windows 上跑了很久的「有记忆」agent，其实什么都没存。修复提交（60b1227）打上了 fcntl shim，病史逐字留在 `backend.py` 的注释里。

**事故二：TUI 静默无记忆。** TUI 的装配路径曾经写死 `backend=None`，每一次 store 和 recall 都是无声的 no-op，配好了模型的用户在 TUI 里始终没有长期记忆（PR #71 修复）。这次事故还牵出第二个坑：EverOS 未配置时的 logger 直接往 stdout 打印，会冲垮全屏 TUI。

**事故三：一个拼写错误。** `mode` 配成 `"embeded"`（少个 d），曾经会落进静默 no-op 适配器。现在构造期校验枚举直接抛 ValueError，`_validate_config` 的 docstring 原文把前因后果写全了：leaving the agent running with memory quietly disabled... surfaces the mistake at construction。

三次事故一个主题：记忆静默消失比记忆失败更危险，因为用户以为它记得。fail-closed 不是洁癖，是对这个主题的三次赔付。

反面也如实说：这套纪律的覆盖不是全库均匀的，`docs/architecture/operations.md` 明写 Loader behavior is not uniformly fail-closed，不许宣称每一种配置错误都会被拦住。

## 六、EverOS 适配器：811 行都在处理边界

适配器本体 `pico/plugin/memory/everos/backend.py`，几个值得深挖的决定：

**import 推迟三层。** 包的 `__init__.py` 不 import backend（插件发现会碰它，必须保持廉价）；真正的 everos 符号在适配器构造时才 import（缺包在构造期就炸，不会拖到第一次 recall 才神秘失败）；embedded 模式下连适配器构造都推迟到 `start()`，并且丢进 `asyncio.to_thread`，因为 everos 加 lancedb 的 import 要 2 到 3 秒同步 CPU，不能堵在渲染路径上（这是 PR #157 的性能修复）。

**双轨的所有权映射就一行。** 存储时每条消息按角色定归属：

```python
"sender_id": agent_id if role in ("assistant", "tool") else (m.get("sender_id") or user_id),
```

assistant 和 tool 消息归 agent 轨（将来蒸馏成 cases 和 skills），用户消息归 user 轨（episodes 和 profile）。召回时反向展平：user 轨回 episodes 加 profiles，agent 轨回 skills 加 cases（case 的 text 用 task_intent 拼 key_insight，注释说这比单独的 intent 更适合做 prompt bullet）。

**embedded 模式要驱动 lifespan。** everos 的表结构和提取引擎建在它 FastAPI 应用的 lifespan 里，不是首次调用时。适配器必须手动驱动这个 lifespan（进程级单例加引用计数），否则 store 直接撞 no such table: unprocessed_buffer。这类「上游的启动语义长在别处」的坑，注释里写得清清楚楚。

**降级也要显式。** agent 轨的混合检索要走 everos 的 cross-encoder 通道，没配 rerank provider 时 everos 会拒绝。适配器的处理是降到纯向量检索并 warn 一次，不是吞掉。

**版本钉死。** `everos[multimodal]==1.1.2`，精确 pin。文档给了理由和八步升级流程，还有一句值得背下来的警告：Do not test an uncharacterized upgrade against the operator's only Memory root。适配器依赖的是上游内部 API，补丁版本都可能挪符号。

## 七、记忆怎么进 prompt，怎么被写回

**读路径（每轮）。** 第 3 段的 builder 干两件事：从 user.md 里按当前消息选相关小节（top-2，标题命中权重是正文的 3 倍，得分为零的小节不做填充凑数，`## Notes` 永远保留），加上 backend.recall 的 top-5 命中，合在一个 `# Memory` 标题下。召回内容整块用 untrusted 围栏包起来，注释给了原因：召回可能携带从历史不可信输入蒸馏来的内容（投毒），进模型前必须标成未验证。agent 轨在第 5 段消费，作为 SkillForge 两个技能源之一，RRF 权重 0.9（本地手写技能 1.0，理由：自进化的技能任务贴合但没经过人工校验）。

**写路径（每轮之后）。** 顺序即语义：先把本轮消息追加进 Session JSONL，再调 backend.store，最后 feedback。Session 先落盘意味着 store 失败时权威记录已经完整，这条顺序有专门测试钉着（store 抛 RuntimeError 的同时断言 session 里 user/assistant 消息俱在）。store 侧还有个节流阀：everos 是攒够了才提取的模型，适配器按 `flush_every_turns`（默认 1）决定哪次 store 带 is_final 触发提取。

**宿主文件的写纪律。** episodes.md 只追加，每条带时间戳；user.md 的每条 bullet 必须以 `[src: episodes.md @ 时间]` 结尾，没有出处的 bullet 会被清理器删掉；Foresight（对用户未来行为的预测）FIFO 上限 20 条。并发写走 portalocker 文件锁加 compare-and-set，输了竞争就放弃本次写入并记日志，等下次整理把内容折回来。这套锁也是事故换来的：之前 Windows 上的锁是 no-op，并发写 user.md 会互相覆盖。

还有一条容易忽略的联动：`memory_enabled` 是个开关链。backend 为 None 时，个性化整个关闭，Curator 的读记忆工具不注册，第 3 段只剩宿主文件。有个很讲究的测试用「读宿主记忆就抛断言」的探针证明：关闭记忆时连宿主状态都不会被碰。

## 八、取舍：为什么不做 X

**为什么协议只有五个方法？** 上一代 ABC 的教训：接口面大了，第三方插件满足不了，抽象本身变成门槛。五个方法是「host 需要什么」的最小集，不是「后端能提供什么」的并集。

**为什么 host 不读 metadata？** 只有 text 进 prompt，意味着插件没有任何通道把未经渲染层审视的结构化内容漏进上下文。逃生舱留给插件生态内部用，宿主的 prompt 组装保持单一入口。

**为什么召回失败宁可整轮失败？** 三次静默降级事故就是答案。失败的轮次用户看得见、能重试；静默无记忆的轮次用户看不见，错误会在后续每一轮里复利。

**为什么删会话不删记忆？** 文档明写 Session deletion does not promise semantic-Memory erasure，这是已知边界不是疏忽：语义记忆是从多个会话蒸馏出来的，单个会话的删除无法定义「哪些蒸馏结果该跟着消失」。要认这个账，被问隐私类问题时不要吹。

## 九、一次真实翻车：合并 18 分钟后的 revert

主线历史上有一次记忆子系统的整体重构被火速回滚。PR #9 合并了一批召回改进：召回改成 on-miss（本地记忆没命中才查 EverOS）、每轮 store 改成阈值触发加夜间批处理、过滤当前会话命中防止和活历史重复。12 个文件，+498/−39。18 分钟后，revert（a194ce4），逐字回滚。

仓库里没有留下书面理由，这一点如实说。但从改动本身能读出方向冲突（标注：这是推断）：那次重构把「记忆一定被写入」变成了「攒到阈值或夜里才写入」，把「每轮召回」变成了「未命中才召回」，两条都和后来写进架构不变量的 fail-closed 语义相反；而且一次跨 8 个模块的行为面改动 18 分钟内回滚，更像是评审未完成就进了主干。后续没有重做：那批机制（on-miss、阈值、夜间任务）在当前代码里 grep 不到任何残留，今天的实现依然是每轮无条件召回、每轮 store。

这个故事在面试里的用法：被问「你们的记忆写入策略为什么这么激进（每轮都写）」时，可以答我们试过更省的方案并且回滚了它，写入语义是架构级承诺，不能为了省调用把「一定记住」变成「大概率记住」。有 commit 可查的取舍，比编一个理由可信。

## 十、怎么被验证

分四层。协议层有一份随包发布的契约测试基类（不在 tests/ 里，在包内，插件作者继承就能跑）：八个断言里最讲究的一条是 store 后故意不断言「刚存的内容立即可召回」，因为很多后端异步建索引，这个断言会把合法实现误杀。适配器层三个文件覆盖 fail-closed 主战场：mode 拼错必须抛、recall/store 在 start 前必须抛、adapter 异常必须传播、双 track id 或零 track id 返回空。链路层的五个关键测试前面提过：全链路、并发轮次证据不串、无 backend 不碰宿主状态、store 失败在 session 保存之后浮出、feedback 失败不破坏 turn。门层是 V-O0（M3）：九个确定性文件里两个直接测记忆，外加一项必需的 live 检查，跨进程证明「换个进程还认得」；live 层的证据词表把 passed、provider_failure、infrastructure_failure、inconclusive、skipped 分得清清楚楚，缺凭证不算通过。

能力边界也在这里如实挂出：检索质量没有 recall@k 式的独立 benchmark，现有评估是分层 e2e（提取质量、端到端、连续性），断言全部结构化加关键词，不做精确匹配，因为上游 LLM 提取非确定。被问「召回准确度怎么评估」，这是诚实答案的底。

## 十一、预演追问

**「记忆系统是怎么设计的？」**（6 次高频）
可以直接说的版本：分三层。会话内的工作状态和无损档案归上下文引擎管；跨会话的长期记忆分两半，一半是人可读的 markdown 档案（用户画像按小节选相关的进 prompt，情节日志只追加、每条带出处），另一半是语义召回，走一个五方法的后端协议，默认实现是双轨的：用户的事实和偏好一轨，agent 自己沉淀的操作技能一轨，存储时按消息角色分流，召回时各自进 prompt 的不同段。全链路 fail-closed：后端选了就必须能用，构造、启动、召回任何一步失败都显式上抛，唯一的关闭方式是配置里明写 null。

**「怎么保证记忆不过期、不会拿旧事实继续推理？」**
分两半答。档案侧有出处纪律：画像里每条结论必须挂着情节日志的时间戳引用，没出处的条目会被清理；小节按当前问题相关性选择，旧结论不相关就不进 prompt。召回侧诚实讲边界：语义库没有逐条的新鲜度校验，防线在消费端，召回内容整块围栏成未验证材料，模型被指示把它当参考不当指令；加一条兜底，当前请求和当前工作区状态的优先级永远高于召回。过期治理是这层的已知短板，不吹。

**「不同层的记忆冲突了怎么办？」**（真实考过）
按信任层级：当前请求最高，其次当前会话的观察，然后是宿主档案，最后才是语义召回（它是围栏材料）。结构上冲突不需要仲裁器，因为四层在 prompt 里的位置和标记不同，模型能看到谁新谁旧、谁验证过谁没有。真正危险的是把召回内容放在和系统指令同等的位置，我们用围栏明确避免了这件事。

**「后端挂了会发生什么？」**
按阶段背拦截链：启动失败缓存并重抛，进程起不来；运行中召回失败，这一轮直接失败，用户看到错误；store 失败，轮次报错但会话记录已完整，不丢对话。唯一静默的是 feedback，它被明确定义为尽力而为的遥测。然后把三次静默降级事故讲一个，说明为什么宁可失败也不装没事。

**「为什么不直接用 mem0 这类现成记忆库？」**
协议层面其实兼容，五方法协议就是按「平轨后端也能实现」设计的，文档里点名 mem0 的接法。选择自带双轨实现的理由：用户事实和 agent 技能的所有权必须分开（一个进第 3 段当背景，一个进第 5 段当技能来源，权重都不同）；召回要可解释、失败要显式，这两条是协议约束，不是库特性。价值在协议和纪律，不在具体引擎，引擎是可插拔的。

## 口播稿

> Pico 的长期记忆是协议加插件的结构：宿主只定义五个方法的 MemoryBackend 协议，召回、存储、反馈、启停，默认插件是双轨实现，用户的事实和偏好走一轨，进 prompt 的记忆段；agent 自己沉淀的技能走另一轨，进技能路由，两轨在存储时按消息角色分流。旁边还有一层人可读的档案：用户画像按相关性选小节，情节日志只追加，每条结论必须带出处引用。这层设计最硬的一条纪律是 fail-closed：后端选了就必须能用，构造、启动、召回任何一步失败都显式上抛，唯一合法的关闭是配置写 null。这条纪律是三次真实事故换来的，Windows 上静默降级成无记忆、TUI 装配漏了后端、一个拼写错误落进 no-op，三次的共同点是用户以为它记得。召回内容进 prompt 前整块围栏成未验证材料，防历史投毒。边界也认账：反馈通道目前是 no-op，检索没有独立 benchmark，删会话不承诺删记忆。
