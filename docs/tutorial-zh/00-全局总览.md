# 00 全局总览：为什么需要一个 Turn 模型

- agent 循环本身只有几十行，harness 到底在解决什么问题

## 一、问题：agent 循环写完之后，麻烦才开始

一个能跑的 agent 循环真的不难写：

```python
while True:
    user_input = input()
    messages.append({"role": "user", "content": user_input})
    resp = llm(messages, tools)
    while resp.tool_calls:
        执行工具、把结果塞回 messages、再问一次
    print(resp.text)
```

它在终端里工作得很好。然后需求来了：同事想在群里 @它；你想让它每天早上九点自动巡检一件事；另一个同事想要个像样的终端 UI。最直接的做法是给每个入口复制一份循环，或者在一个循环外面套 if。这条路上埋着六个坑，每个都在真实项目里翻过车：

1. 状态分家。CLI 里聊过的事，群里那份循环不知道；要么强行共享一个全局 dict，并发一来就写脏。
2. 并发踩踏。加一把全局锁，一个人卡住全员；不加锁，同一个群连发两条消息，两份循环交叉写同一段历史。
3. 资源抢占。早上九点定时任务开跑，占着模型配额，用户的提问排在它后面干等。
4. 交付丢失。平台 API 抖一下，回复就没了；重试逻辑散落在各个业务循环里，写了三遍还各不相同。
5. 停不下来。用户说「停」，你发现能停的最小单位是整个进程。
6. 无从复盘。每个入口一种日志格式，出了问题连「刚才发生了什么」都拼不出来。

这六个坑合起来就是 harness 这个词的由来：agent 决定下一步做什么，harness 规定它在什么边界内做、怎么排队、怎么交付、怎么记录、什么时候算完成。模型能力解决不了其中任何一条。

## 二、Pico 的答案，先给一句话

一个 Runtime、一个 Turn 模型、五个执行面（M8）。不管请求来自 CLI、终端 UI（TUI）、后台 Gateway、定时 Cron 还是聊天平台 Channel（飞书、QQ、企业微信三个适配器，M9），都变成同一种值（`TurnRequest`），从唯一入口（`Scheduler.submit`）进一条调度骨干（Spine），按会话串行执行，产出统一的事件流（Deliverable）交给交付层（DeliveryHub）。上面六个坑，每个都有一个具名部件负责，本章挨个走到。

先框定它是什么、不是什么。Pico 是通用 agent harness，刻意不做 coding agent 特化；仓库的大头花在模型外面。规模感（按基线 `76d3761` 的 git 追踪文件计数）：`pico/` 下 328 个 Python 文件、约 6.7 万行（wc -l 实测 67507）、22 个顶层子包；工作树里还能看到一个空的 `skill_hub/`，它未被 git 追踪，`docs/architecture/README.md` 点名这类空缓存目录不代表保留能力。`tests/` 下 247 个 Python 文件，其中 232 个是 `test_*.py`，其余是 conftest 与辅助模块。`ui-tui/` 是 React + Ink 的终端前端，`src/` 下 185 个 TS 文件（内含 58 个测试文件），另有内嵌的 hermes-ink 渲染包，全仓追踪的 TS 文件共 320 个，全部只通过 TUI-RPC 和 Runtime 通信。全库还有一个贯穿性立场：能力声明必须带证据等级，确定性、契约、live、fixture、历史这几类不互换（架构不变量第 9 条），本章末尾会用它盘点现状。

## 三、唯一的输入：TurnRequest

全系统只有一种输入类型。`pico/spine/turn.py` 整个文件 40 行，核心部分照抄：

```python
class Origin(StrEnum):
    """Who the request belongs to — drives pool, control eligibility, accounting."""
    USER = "user"
    CRON = "cron"
    SUBAGENT = "subagent"

class BusyPolicy(StrEnum):
    """What to do when the conversation's lane is already busy."""
    APPEND = "append"
    INJECT = "inject"
    INTERRUPT = "interrupt"

@dataclass(frozen=True)
class TurnRequest:
    origin: Origin
    source: Source            # channel, chat_id, sender_id, chat_type, extras
    text: str
    media: tuple[Media, ...] = ()
    message_id: str | None = None
    conversation: str | None = None
    busy: BusyPolicy = BusyPolicy.APPEND
```

每个字段都在替一个坑做决定，逐个看：

- `origin` 决定进哪个并发池（第六节），也决定记账归属和控制命令资格。用户、定时任务、子代理三种身份从类型上分开，坑 3 的答案从这里开始。
- `conversation` 决定进哪条 Lane（每会话一条串行通道）。同一个群的消息天然排队，不同群互不影响，坑 2 的答案。
- `busy` 决定撞车时怎么办，三种策略对应三种真实场景。APPEND 是默认：排队等前一个 turn 做完。INJECT 用在聊天平台：会话正忙时又来一条消息，不打断当前执行，把新消息塞进工具循环的间隙合并处理（Gateway 的入站分发用 `scheduler.has_inflight` 探测会话忙，忙就切这个策略）。INTERRUPT 是打断：取消当前 turn，把新请求插到队首，排在所有 APPEND 积压前面。
- `message_id` 是入站消息自己的 id，回复出站时作为 reply_to 锚点线程回去，群聊里的回复不会飘。
- `frozen=True` 不是装饰：请求进了调度器就不可变，排队期间没人能改它。

三种撞车策略还有一条资格线，几乎所有人第一遍都会漏：INJECT 和 INTERRUPT 只有 `Origin.USER` 能用。`scheduler.py` 的 `_effective_busy` 在提交点把非用户来源的这两种请求降级成 APPEND，并把「请求了什么、实际用了什么」写进日志：

```python
def _effective_busy(self, req: TurnRequest) -> BusyPolicy:
    if req.busy is BusyPolicy.APPEND or req.origin is Origin.USER:
        return req.busy
    logger.info(
        "busy policy demoted: origin={} requested={} applied={}",
        req.origin,
        req.busy,
        BusyPolicy.APPEND,
    )
    return BusyPolicy.APPEND
```

动机很具体：定时任务算错触发时间，不该有能力取消用户正在跑的 turn。可迁移的做法是把「谁能对谁做什么」的资格判断收在唯一提交点做完，五个入口就都不用各自防一遍。

## 四、唯一的接缝：TurnRunner

调度骨干和 agent 实现之间只有一个协议，`pico/spine/runner.py` 全文 41 行，核心是这几行：

```python
Emit = Callable[[RunnerEvent], Awaitable[None]]
Drain = Callable[[], list[TurnRequest]]   # 读并清空本 Lane 的 INJECT 队列

@dataclass(frozen=True)
class TurnOutcome:
    """What a finished run hands back; the worker fills TurnEnded from it."""
    usage: Usage
    explicit_reply: bool
    tool_calls: int = 0
    tool_failures: int = 0
    memory_hits: int = 0
    injected_skill_ids: tuple[str, ...] = ()
    context_path: str | None = None
    context_fallback_reason: str | None = None
    skill_source_failures: tuple[str, ...] = ()

@runtime_checkable
class TurnRunner(Protocol):
    async def run(self, req: TurnRequest, emit: Emit, drain: Drain) -> TurnOutcome: ...
```

可以拿插座打比方：Spine 定义插座标准（协议），AgentLoop 是插上来的电器。好处很实际：调度、排序、取消这些逻辑可以拿一个假 runner 单独测试，模型一次都不用调。文件 docstring 把意图写明了：spine defines the `TurnRunner` protocol and the agent loop implements it; spine never imports the agent。想验证不是嘴上说说，一条 grep：

```bash
grep -rE "^(from|import) " pico/spine/ | grep -v "pico\.spine"
# 输出只有标准库和 loguru，没有任何 pico.agent / pico.providers / pico.cli
```

输出词汇表也在这层钉死。runner 能 emit 的只有内容事件：`Text | MediaOut | StreamDelta | Reasoning | Notice | ToolEvent`（统称 Deliverable）；生命周期事件 `TurnStarted / TurnFailed / TurnEnded` 归 Spine 的 worker 发。这条规矩有运行时执法：scheduler 在 emit 边界做类型检查，runner 试图发生命周期事件直接 `TypeError`。实现上有个细节值得在面试里讲：守卫用 `get_args(RunnerEvent)` 展开成元组做检查而不是直接用 union，注释写了原因，防止将来上了类型检查器后有人以为该分支不可达把守卫删了。docstring 里也承认：仓库没有静态检查器，类型窄化只是意图，真正的执法在 scheduler。

emit 的守卫旁边还有一次身份补齐。runner 发出的事件如果没填 `source` 或 `conversation_id`，Lane 的 emit 包装用 `dataclasses.replace` 盖上这个 turn 的回复地址和会话键，已填的从不覆盖（`scheduler.py` 的 `_make_emit`）：

```python
if event.source is None:
    event = replace(event, source=req.source)
if event.conversation_id is None:
    event = replace(event, conversation_id=self._conversation_id)
```

这两行让 runner 不必知道自己在替哪个会话干活；回复地址由调度层从 TurnRequest 里带过来，业务代码里就不会出现「回错群」这类手写路由错误。

`drain` 的注释里还藏着一条设计意图：runner 可以完全无视 drain（原话 the minimal-legal implementation never drains）。没被取走的 INJECT 消息在 turn 结束时由 worker 回落成一条普通的 APPEND turn，消息不丢，只是少了「合并进当前轮」的优化。协议的可选能力照这个思路设计，最懒的实现也保持正确，做了增强只会更好。

`TurnOutcome` 的字段设计回应坑 6：工具调了几次、失败几次、记忆命中几条、上下文走了哪条路，结构化地交回去，worker 原样填进 `TurnEnded`。任何 host 不用解析渲染文本就能核对同一个 turn 的完成情况。

## 五、一条命令的完整旅程

先修正一个几乎人人会写错的命令：message 是选项不是位置参数，`pico run "..."` 会报错，正确写法 `pico run -m "..."`。`pico run` 不带 `-m` 进交互 REPL，裸 `pico` 进 TUI。

```
pico run -m "总结一下这个仓库"
  │  pico.cli.commands:run             console script（pyproject.toml）
  ▼
agent_commands.agent()                 读配置 → make_provider → CronService
  ▼
assemble_runtime()                     SessionManager / 插件注册表 / Memory Backend / AgentLoop
  ▼
build_repl()                           DeliveryHub + CliOutlet + Scheduler(AgentTurnRunner)
  ▼
Scheduler.submit(TurnRequest) ──► Lane（每会话一条，串行）
                                    │  取 OriginPools 信号量，worker 发 TurnStarted
                                    ▼
                    AgentTurnRunner.run（一行转发）
                                    ▼
                    AgentLoop.run_turn
                                    │  _process_message：hooks、会话、上下文装配
                                    │  _run_agent_loop：LLM ↔ 工具迭代（上限 40 轮）
                                    ▼
                    emit(Text / MediaOut / StreamDelta / …)
                                    ▼
                    DeliveryHub（每 outlet 一队一 worker）──► CliOutlet ──► 终端
                                    ▼
                    worker 发 TurnEnded；hub.wait_idle 之后才 teardown
```

每一站说清楚它在防什么：

1. `agent_commands.agent()` 先 `load_runtime_config`（内部 `set_config_path`，必须最先跑，后面所有组件按同一份配置装），然后 `make_provider`、建 `CronService`。
2. `assemble_runtime()` 是三个 host 共用的唯一组合根（第八节细讲）。为什么强调唯一：坑 1 的根源就是每个入口各装一套、各持一份状态。
3. `build_repl()` 造交付侧。注意顺序：交付层先就位，再开始跑 turn，回复永远有地方去。
4. `scheduler.submit(...)` 返回 `TurnHandle`。这里有个容易答错的细节：`handle.result()` 只代表 runner 不再产出事件，不代表回复已经渲染；渲染屏障是 `hub.wait_idle("cli")`，CLI 一次性模式必须等它再退出，不然进程退了回复还在队列里。收尾还有一条脚本能感知的约定：`result()` 返回 None（取消或失败）时，一次性模式以 `typer.Exit(1)` 结束，退出码区分成败。
5. Lane 的后台 worker 取信号量、发 `TurnStarted`，然后调 runner。`AgentTurnRunner.run` 只有一行转发，接缝薄到没有逻辑可藏。
6. `run_turn` 不 catch 异常（docstring 明说），异常穿透回 Lane 转成 `TurnFailed`，错误处理收在一处。Gateway 的 sink 在收到非取消的 `TurnFailed` 时还会给用户回一条错误文案，失败不无声。
7. CRON 起的 turn 在进入前先 `set_cron_context(True)`：定时任务执行中不允许再给自己排定时任务，防自我复制。

## 六、排序、并发、交付各归各管

三个部件，三个正交维度，每个用一个场景讲。

**Lane：同会话串行，跨会话并行，取消按会话。** 场景：群 A 连发三条消息，全部进同一条 Lane 排队，严格按序执行，历史不会交叉写（坑 2）；群 B 的 Lane 独立推进，A 里一个慢工具卡 60 秒，B 完全无感。用户喊停，取消的单位就是 Lane，不用重启进程（坑 5）；/stop 落到 `cancel_conversation`，跑着的 turn 取消其 task，排队的直接解析成取消，mailbox 里还没被合并的 INJECT 一并清掉。工程参数：pending 队列深度到 50 打一次警告；空闲 300 秒被 reaper 回收，60 秒扫一次；INJECT 的消息进的是 Lane 自己的 mailbox，等 runner 在迭代间隙来取，turn 结束还没被取走的由 worker 回落成新的 APPEND turn。术语提醒：Lane 不叫 queue，它同时是排序单位和取消域，CONTEXT.md 专门立了词条。

**OriginPools：用户和系统各一把信号量，互不借用。** 场景：九点整三个 cron 一起醒来，全挤在 system 池（Gateway 默认 2 个槽）里排队；用户此刻提问，走 user 池（默认 4 个槽），完全不等（坑 3）。REPL 下两池各 1。CRON 和 SUBAGENT 共用 system 池（`_SYSTEM_ORIGINS` 元组写死这两种）。没有全局上限，也不借用；未知 origin 直接 `ValueError`，注释原话 fail-loud：新加一种 origin 必须显式选池，不许被 fallback 默默塞进 system 池。

**DeliveryHub：每个 outlet 一条队列一个串行 worker。** 场景：飞书 API 抖动，投递失败重试 3 次（1、2、4 秒退避）；重试期间飞书的队列（上限 100）慢慢积压，但只堵飞书这个 outlet，CLI 和 TUI 照常出活（坑 4）。Outlet 的契约里有一条容易讲错：渲染不了不算失败。表达不了某类事件的 outlet 把它吃掉、正常返回、自己记跳过日志；只有传输错误这类真失败才抛异常触发重试。重试耗尽后事件记 error 日志然后丢弃，已完成的 turn 不会被回头改成失败；出站队列只在内存里，没有持久化，这条明确列在 `docs/architecture/README.md` 的当前风险清单里。交付整个在 Agent Loop 之外（不变量第 6 条）：runner 只发类型化事件，怎么渲染、发到哪个平台、失败了怎么办，全是交付层的事。

关停也归这一层的语义管。`Scheduler.shutdown` 分四个阶段：封死入口（此后 submit 直接抛 `SchedulerDrainingError`）、把排队中和 mailbox 里的未启动工作全部解析成取消、给正在跑的 turn 一个宽限窗口、超时的级联取消。封死和清队之间没有 await，不给「刚提交的请求掉进正在关闭的缝里」留时间窗；四条退出路径（正常、失败、取消、关停）都保证解析 turn 的 future，调用方的 `result()` 不会永远挂着。

回头对一下账：

| 开头的坑 | 接住它的部件 |
|---|---|
| 1 状态分家 | 唯一组合根 assemble_runtime + Session（第 06 章） |
| 2 并发踩踏 | Lane 按会话串行 |
| 3 资源抢占 | OriginPools 双池隔离 |
| 4 交付丢失 | DeliveryHub 队列 + 重试 + 背压 |
| 5 停不下来 | Lane 即取消域 |
| 6 无从复盘 | Deliverable 词汇表 + TurnOutcome + Tracing（第 09 章） |

## 七、AgentLoop 内部：三层结构

第一版的坑常出在这里：把 AgentLoop 说成「一个循环」。它实际是三层，各干各的。

**第一层 `run_turn`：扇出适配。** 它不做业务，做翻译：注册五个回调把内部事件翻成 spine 事件（`on_token` 到 `StreamDelta`、`on_reasoning` 到 `Reasoning`、`on_tool` 到 `ToolEvent` 的 START/COMPLETE、进度到 `Notice`、媒体到 `MediaOut`）；把 message 工具的发送回调也接到同一条流上，工具主动发的消息和最终回复走同一个出口。收尾处是单一 return→emit 边界：媒体先发，非流式时再发一条 `Text`。最后拼 `TurnOutcome` 交回。全程不 catch 异常。

**第二层 `_process_message`：单轮编排。** 按序做完一轮的固定动作：`hooks.before_user_inbound`（插件可在这里短路整轮）；`sessions.get_or_create` 拿会话；拦截 `/new`、`/help` 这类斜杠命令；调上下文引擎 `assemble`（第 03 章的全部内容发生在这一行里）；模型路由选链；进第三层跑迭代；回来后按序落盘：`_save_turn` 把本轮消息追加进会话 JSONL、`context_engine.after_turn` 让引擎做轮后整理、再把记忆的 store 和 feedback 分发给后端（两个动作都有独立 tracing span）。顺序本身是约定：先保交易记录（session），再做衍生加工（记忆），崩在中间时权威记录是完整的。

**第三层 `_run_agent_loop`：迭代循环。** `while iteration < max_iterations`（默认 40，配置项 `max_tool_iterations`），循环内每轮九个动作，加两个循环外的收尾，值得逐个过：

1. `drain()`：把 INJECT 进来的新消息在这个间隙合并进上下文。这就是 BusyPolicy.INJECT 承诺的兑现点：不打断工具执行，在两次迭代之间接活。
2. 取当前工具定义（工具集这轮可能变，比如 MCP 刚连上）。
3. TokenWise 的 `before_llm_call` 钩子：缓存断点在这里注入（第 04 章）。
4. 调 provider：流式走 `_llm_call_stream`，非流式走 `chat_with_retry`。
5. `after_llm_call` 钩子回收用量，填 usage sink。
6. 上下文溢出的抢救路径：provider 报窗口超限，`_emergency_shrink` 把较早的工具结果正文替换成占位符（原文 `[earlier tool output elided to fit the context window]`），保住最近 3 个工具结果和全部 system/user/assistant 消息，然后重试本轮，最多 2 次。被溢出打断的那次调用不计入 40 轮预算，代码里是 `iteration -= 1`，注释原话 the overflowed call did no work; don't bill it。
7. 有 tool_calls：把 assistant 消息进上下文，逐个 `tools.execute` 执行，结果回填。没自带 `timeout_seconds` 的工具吃注册表 300 秒的兜底上限，注释写明这个上限防挂死，不是逐工具 SLA。
8. 同一个工具连续 2 次确定性失败（`_LOOP_BREAK_THRESHOLD`，瞬时错误不计入）：往最后一条工具结果后面追加一条 loop-break nudge 提醒模型换路，每 turn 最多注入 2 次，防提醒本身变成新的循环。
9. 没有 tool_calls：空响应分类器给出四种处置：PREFILL（模型只输出了思考没输出正文，把思考喂回去让它接着写）、NUDGE（工具刚执行完就交白卷，插一条催促）、RETRY（普通空响应，原样重发）、COMPLETE（认定完成）。恢复用的脚手架消息都带 `_recovery_synthetic` 标记，落盘前统一剥离；模型返回错误的那轮响应也不进会话历史，注释引 #1303：错误文本会污染上下文造成永久 400 循环。
10. 迭代打满 40 轮：进 Synthesis，禁用工具做最后一次收尾调用，turn 状态记 `interrupted`。合成调用本身失败还有一条静态兜底文案，turn 不以沉默收场；合成出的答复也追加进会话历史，下一轮做中断恢复时看得见。注意它由迭代数触发，不是超时，面试官常拿这个抠。
11. 循环退出后 `checkpoint.commit_turn`：本 turn 的全部 workspace 变更打成一个提交进影子 git（`<workspace-state>/shadow.git`），注释写明对齐 Claude Code/Cursor 的按 turn 粒度，改坏了可回滚；best-effort，commit_turn 从不抛异常。

## 八、一次装配，五个入口

`assemble_runtime()`（`pico/cli/_runtime_assembly.py`，全文 145 行）是唯一的组合根，装配顺序固定：SessionManager、插件注册表、Memory Backend、插件工具、AgentLoop（29 个具名参数）、个性化开关。资源释放也归它，这段值得贴原码：

```python
async def close(self) -> None:
    try:
        if not self._agent_closed:
            try:
                await self.agent_loop.close_mcp()
            except Exception:
                logger.exception(
                    "agent runtime close failed; continuing shutdown",
                )
            else:
                self._agent_closed = True
    finally:
        if self.backend is None:
            self._backend_stopped = True
        elif not self._backend_stopped:
            try:
                await self.backend.stop()
            except Exception:
                logger.exception(
                    "memory backend stop failed; continuing shutdown",
                )
            else:
                self._backend_stopped = True
```

三个可讲的点：MCP 先关、记忆后端一定被走到（`finally`）；每步吞异常继续，关停路径上一个组件的失败不连坐；两个幂等标志防重复关。启动侧同样克制：`start_memory_backend()` 只试一次，失败被缓存并在后续调用重新抛出。选了记忆后端但起不来，系统不会装作没有记忆继续跑（不变量第 5 条，fail-closed）。

五个入口各自的适配点，共用上面这一套：

| 入口 | 适配文件 | 提交点 |
|---|---|---|
| CLI（一次性 / REPL） | `pico/cli/agent_commands.py` + `_repl_spine.py` | `scheduler.submit(TurnRequest(origin=USER, channel="cli", ...))` |
| TUI | `pico/tui_rpc/spine.py` + `methods/turn.py` | Node 前端经环回 JSON-RPC 调 `turn.send`，方法内 submit；Lane 忙时报 `TurnInProgressError`（错误码 -32003） |
| Gateway | `pico/cli/_gateway_spine.py` | 每个 channel 注册一个 `ChannelOutletAdapter`；`TurnFailed` 非取消时回固定文案 `Sorry, I encountered an error.` |
| Cron | `pico/cli/_cron_handler.py` | `TurnRequest(origin=CRON, conversation="cron:<job.id>")`，回复走 readback，多目标任务把回复逐个 `hub.post` 广播给每个目标 |
| Channel（飞书/QQ/企微） | `pico/channels/intake.py` + `gateway_commands.py` 的入站分发 | 平台事件 → 白名单检查（deny-by-default，`allow_from` 为空全拒） → submit；会话忙时切 `BusyPolicy.INJECT`；`/stop` `/restart` 在分发层拦截不进 agent；会话正卡在 ask_user 提问时，来的消息被当成答案路由给 QuestionBroker，不另起 turn |

第六个入口藏在配置里：subagent 的结果以 `Origin.SUBAGENT` 重新 submit 回 Spine（`agent_loop.subagents.set_submit(scheduler.submit)`），三个 host 都接了这根线。子代理有自己的工具集和并发上限（`max_concurrent_subagents` 默认 4，`max_subagent_spawns_per_hour` 默认 30，配置默认值在 `pico/config/schema.py`；限额按会话记滚动一小时窗口，一个会话刷爆额度不影响别的会话），但它的产出走正门，不走旁路。

## 十二、预演追问

**「讲一下从输入命令到 agent 执行完毕的整条链路。」**（4 次真实考过）
能直接说的版本：入口只有一个，任何来源的请求先变成 TurnRequest，带着身份、会话和撞车策略，从 Scheduler.submit 进来。调度层按会话分 Lane 串行排队，按身份分池控并发，worker 发 TurnStarted 之后把请求交给 runner 协议的实现，也就是 AgentLoop。AgentLoop 三层：外层把内部事件翻译成统一事件流，中层做单轮编排（上下文装配、会话落盘、记忆分发），内层是 LLM 和工具的迭代循环，上限 40 轮，打满转 Synthesis 收尾。产出的事件进交付层，每个出口一条队列一个 worker，带重试和背压，最后 worker 发 TurnEnded 收口。一个入口、一条通路、一份事件词汇表，CLI、TUI、网关、定时、聊天平台五个面共用。

**「harness 是什么？在你项目里怎么体现？」**（5 次高频）
agent 决定下一步做什么，harness 规定它在什么边界内做、怎么排队、怎么交付、怎么记录、什么时候算完成。落在这个项目里就是本章的六个坑和六个部件：统一输入类型管边界，Lane 管排序和取消，双池管资源隔离，DeliveryHub 管交付可靠性，TurnOutcome 和 tracing 管记录，验证门管「算不算完成」。可以补一句：这些部件每个都能脱离模型单独测试，这是把它们从业务循环里拆出来的最大收益。

**「Agent Loop 是怎么实现的？」**
三层：扇出适配层不做业务只做事件翻译，而且不 catch 异常，失败穿透回调度层统一转 TurnFailed；编排层按固定顺序走 hooks、会话、上下文装配、落盘，先保权威记录再做衍生加工；迭代层每轮先合并注入消息、再过缓存钩子、调模型、执行工具，配了四类空响应恢复、工具连败的断环提示、上下文溢出的两次抢救，40 轮打满转 Synthesis 禁工具收尾。turn 结束时把本轮全部 workspace 变更打成一个提交进影子 git，可回滚。

**「为什么不用现成框架 / Claude Code？」**（7 次高频，完整话术在 90 章）
方向：编排框架解决的是「把节点连成图」，这个项目的难点在图之外：同会话串行和取消语义、用户和系统任务的资源隔离、交付层的重试背压、记忆和工具的 fail-closed 边界、证据分级。这些是运行时契约，不是编排问题。演示会用框架和演示能定契约，是两份不同的能力证明。

**「如果两个群同时 @机器人，一个卡住了会怎样？」**（并发场景题的通用形态）
两个群是两条 Lane，各自串行、互不阻塞；卡住的那条也不会无限占资源，单工具 300 秒兜底超时、迭代 40 轮封顶。同一个群里追问怎么办：会话忙时新消息按 INJECT 策略进 mailbox，runner 在迭代间隙合并处理，不打断执行中的工具；直到 turn 结束都没被合并的，回落成一条新的排队 turn，消息不丢。还可以反向补一刀：系统任务想打断用户做不到，非 USER 来源请求 INTERRUPT 或 INJECT 会被 `_effective_busy` 降级成 APPEND 并留日志。

**「用户说停，正在跑的东西怎么收场？」**（攻击路径 6「失败路径拷问」的常见变体，取消细节在第 01 章展开）
/stop 落到 `cancel_conversation`：跑着的 turn 取消它的 asyncio task，取消异常穿透回 Lane 转成 `TurnFailed(cancelled=True)`；排队中的直接解析成取消，不会再跑；mailbox 里没合并的注入消息一并清掉，已合并的跟宿主 turn 同命运。Gateway 的 /stop 还顺带取消该会话的子代理，回一句 Stopped N task(s)。进程级关停是另一件事，走 `Scheduler.shutdown` 四阶段：封死入口、清未启动工作、宽限窗口、级联取消；每个 turn 的 future 保证在四条退出路径之一上被解析，调用方的 `result()` 不会悬挂。

## 口播稿

> Pico 是一个通用 agent harness，核心设计是一个 Turn 模型。不管请求来自命令行、终端 UI、后台网关、定时任务还是聊天平台，都先变成同一种不可变的 TurnRequest，从唯一入口进调度骨干：按会话分 Lane 串行执行，Lane 同时是取消域；按请求身份分两个并发池，用户永远不等系统任务的槽。执行侧 AgentLoop 分三层，外层只做事件翻译且不吞异常，中层按「先保会话记录、再做记忆加工」的顺序编排，内层迭代循环带空响应恢复、断环提示和溢出抢救，四十轮封顶转收尾合成。产出走统一的事件词汇表进交付层，每个出口一条队列一个 worker，带重试和背压。调度骨干和 agent 之间是依赖倒置的：骨干定义 41 行的协议，从不 import agent，一条 grep 可验。证据侧三千多项确定性测试加连续性、进化两道验证门，live 证据单独标新鲜度。这套东西回答的是同一个问题：agent 循环之外，怎么让系统可排队、可取消、可交付、可复盘。
