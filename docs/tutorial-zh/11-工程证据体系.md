# 11 工程证据体系：让「我做了 X」这句话可被检验

> 教学快照：代码正文按 `76d3761`（PR #47）阅读，第一轮证据核实至 `b65f962`（PR #53）；当前检查点为 `b215c13`（PR #56）。PR #54 刷新 host/V-LP，PR #56 刷新 V-E0/retained，完整 V-R0 未通过。差异与 M 编号见 [references/metrics-ledger.md](references/metrics-ledger.md)。

读完这一篇，你应该能回答：

- 「测试都过了」为什么不等于「这个能力可用」，中间差了哪几层
- 一道门跑完在磁盘上留下什么，别人凭什么信那份东西
- 证据等级和结果状态是两回事，混用会出什么事
- 一次门跑绿，凭什么说它属于这个 commit 而不是上一次
- CI 为什么故意比验收小，小到什么程度
- 这套纪律怎么反过来约束简历和面试话术

本章反复出现的「门」（Gate），在这个仓库里指三件东西的组合：一条写死在 Makefile 里的命令，一份路径固定、带 schema 版本号的 JSON 报告，一个只在真通过时才为 0 的退出码。缺任何一件，它就退化成「有人跑过一遍测试」。

## 一、问题：绿色的三种假象

先看三个都发生过的场景。

**假象一：CI 绿，功能坏。** donor 仓库的日常 Python 检查是 `make test-python`，四个文件 59 个用例，内容是 commit message 策略、大文件策略、CLI 冒烟、LiteLLM 装配。基线文档给它单开了一节，标题就叫 Why `make test-python` is insufficient，里面写着它不碰 Agent Loop、Spine、Tools、Channels、Memory、Sessions、Context、TUI RPC、Sandbox 和安装路径。同一个 commit 上把全量非模型测试跑一遍（`uv run pytest -q -m 'not real_llm and not llm_judge'`），结果是 4383 passed、85 failed、12 errors、20 skipped、8 xfailed。绿灯是真的，覆盖范围也是真的，两者之间没有关系。

**假象二：门跑绿了，但绿的是上一次。** 门把结果写进一个固定路径的 JSON 报告，比如 `.pico/evidence/continuity/continuity-report.json`。时间线是这样的：

```
09:12  V-O0 跑通，写下 continuity-report.json（绑 commit A，status: passed）
10:40  改了 session 的代码，提交成 commit B
10:41  V-O0 再跑，确定性层在写报告之前崩了，进程直接退出
10:41  磁盘上还是 09:12 那份 passed，字节一个没变
10:42  汇总的人（或脚本）读到它，判定通过
```

没有人撒谎，没有一步是错的，结论是错的。

**假象三：跑绿了，但环境不干净。** 打包验证通过，事后复查发现它继承了宿主的凭证和配置，还把有未提交改动的源码当成了 HEAD。这条记录还留在证据索引里，处置栏的原话是 `Passed, but inherited host credentials/config and mislabeled dirty source as HEAD; not trusted`。数字是真的，结论不可信。

三种假象的共同结构：绿色是一个信号，但信号本身不携带「它测了什么、属于哪个 commit、在什么环境下测的」。证据体系要做的就是把这三样元信息变成结构的一部分。

朴素做法及其失效方式，三条都很常见：

- **靠人写发布清单**。人会复用上次的结果，尤其发布前赶时间。清单上的对勾不记录它是什么时候打的。
- **靠 CI 全绿即可发布**。CI 会被逐步调小以求快，没人注意它已经不覆盖核心。假象一就是这条的实测。
- **靠一个覆盖率百分比**。覆盖率回答的是「哪几行被执行过」，不回答「哪个能力有证据」。一句 `import` 能把一个模块的行覆盖率拉起来，但它没有断言任何行为。

一个绿色信号如果不带「测了什么、属于哪个 commit、在什么环境」，它只能证明有人跑过一条命令。

## 二、机制一：门是显式命名的，每个门只答一个问题

拿连续性门当样板，看一份报告长什么样。脚本最后写出去的就是这个字典（`scripts/verify_continuity.py:189`）：

```python
report = {
    "checks": checks,
    "gate": "V-O0",
    "live_mode": args.live_mode,
    "schema": "pico.continuity.evidence.v1",
    "status": status,
}
report_path = output_root / "continuity-report.json"
```

五个字段各有用处。`gate` 说明这是谁的报告；`status` 是结论；`checks` 里每一层带自己的命令、pytest 计数、日志文件名和该日志的 SHA-256，所以「结论」和「原始输出」之间有可核对的链子；`live_mode` 记录这次是要求跑 live 层还是关掉了；`schema` 是格式版本号，格式变了下游能立刻发现（channel 门的证据 schema 就在 PR #50 从 v1 提到了 v2）。

仓库把验证拆成一组这样的门，每个门一条命令、一份报告、一个明确的断言边界：

| 门 | 命令 | 回答什么 | 相对代码基线 |
|---|---|---|---|
| V-D0 | `make test-retained` | 保留的确定性行为有没有回归 | 基线上已有 |
| V-T0 | TUI lint / RPC 检查 / type-check / test / build | 终端前端的契约还在不在 | 基线上已有 |
| V-P0 | `scripts/verify_distribution.py` | 装出来的包在 checkout 之外能不能用 | 基线上已有 |
| 主机门 | `make verify-runtime-hosts` | 装出来的 wheel 上 CLI/TUI/Gateway 行为是否一致 | 基线上已有 |
| V-LP | `make verify-live-provider` | 真实 provider 上一条 Turn 走不走得通 | 基线上已有 |
| V-O0 | `make verify-continuity` | 会话与记忆跨进程连不连得上 | 基线上已有 |
| V-E0 | `make verify-evolver` | 进化流程的生命周期与证据逻辑对不对 | 基线上已有 |
| V-C0 | `make verify-channels` | Channel 契约的确定性覆盖是否成立 | PR #48，晚于代码基线 |
| V-S0 | 同上，一条命令跑两个 bundle | SDK 懒加载、允许名单默认拒绝、单适配器故障隔离 | PR #50，晚于代码基线 |
| V-LF | `make verify-live-feishu` | 真实飞书的收发与重启后 Cron 是否被记录 | PR #48 落 harness，无通过记录 |
| V-TE0 | `make verify-turn-evidence` | 一条 Turn 的 trace、用量、投递证据能不能对上 | PR #51，晚于代码基线 |
| V-R0 | `make verify-release` | 上面所有层是否在同一个 commit 上同时通过 | PR #52，晚于代码基线 |

这张表本身就得绑 commit，而且这份教程亲身演示了为什么。写作时代码正文读的是工作树 `76d3761`（PR #47），`git show 76d3761:Makefile` 上只有前七行那些门；写作期间 main 一路推进到 `b65f962`（PR #53），门的清单跟着变了四次：PR #48 加了 V-C0 与 V-LF harness，PR #50 加了 V-S0 并把 channel 证据 schema 提到 v2，PR #51 加了 V-TE0，PR #52 把 V-R0 的 driver 合了进来。

其中一条尤其值得留在纸上。本章初稿写的是「主干上 `make verify-release` 这个 target 并不存在」，依据是当时的主干状态，还引了一个专门修复「文档指向不存在的 make target」的提交作旁证。收尾复查时这句话已经过期，PR #52 合入后主干上确实有了这个 target。一份讲证据绑定 commit 的文档，自己的断言被 commit 推进作废，这件事比任何论证都更能说明为什么每个声明都要写清「在哪个 commit 上为真」。门的存在与否本身就是需要绑定 commit 的事实，不只是数字需要。

门还有一个容易被忽略的失效方式：它会悄悄缩小。channel 契约门的清单是一个显式常量，注释直接把这个风险写在了上面（`scripts/verify_channels.py`，main）：

```python
# V-C0: every deterministic Channel contract file. Adding a deterministic
# Channel test file means adding it here, or the gate silently stops covering it.
_CONTRACT_TESTS = (
    "tests/test_auth_allowlist.py",
    "tests/test_channels_base.py",
    ...
    "tests/test_verify_channels.py",
    "tests/test_verify_live_feishu.py",
)
```

显式清单和通配符各有代价：通配符不会漏掉新加的文件，但删掉一个文件它也不会报警；显式清单会漏新文件，所以把「加文件要同时加进清单」写成注释挂在常量头上。安全 bundle（V-S0）更进一步，选到测试函数级别，比如 `tests/test_channels_manager.py::test_factory_crash_disables_only_that_channel`。这样一次重命名会让门直接失败，而不是让它安静地少测一条。

## 三、机制二：证据等级不是形容词

最容易被说糊的地方在这里。仓库把两组词写成了两张互不重叠的表（`docs/feature-evidence.md`，main）。

**证据等级**回答「这条证据是什么性质」：

| 等级 | 含义 |
|---|---|
| deterministic | 一组离线可重跑的测试跑过这段代码，不调模型、不走网络、不连聊天平台 |
| contract | 产出的产物或接口对着一份书面规范校验，比如 V-TE0 对 `specs/turn-evidence-correlation.md`、V-P0 对 wheel 清单 |
| live | 真实 provider 或真实平台跑过这条路径，且只对那次通过运行记录的确切 commit 与场景成立 |
| historical | 记录在案的过去运行，外部工件带 digest 和 source commit，不能随时重跑 |

**结果状态**回答「这次跑出来什么」：skipped、inconclusive、provider_failure、infrastructure_failure。文档里那句话必须原样记住：

> `skipped`, `inconclusive`, `provider_failure`, and `infrastructure_failure` are result states, not evidence classes. None of them satisfies a required Gate.

这个区分是代码强制的，不是一句口号。channel 契约门的分类函数注释写得很直白：

```python
def _classify(returncode: int, output: str) -> str:
    """Both bundles are deterministic, so anything short of a clean pass fails.

    A skip or an expected failure is not evidence that a Channel contract holds;
    only a run where every selected test actually passed can pass the Gate.
    """
```

它要求 passed 大于零，且 failed、errors、skipped、xfailed、xpassed 全部为零。这里有两个 pytest 术语要先落地：`xfail` 是「作者预先声明这条会失败」，`xpass` 是「标了预期失败结果却通过了」。两者都意味着测试作者对结果做过一次让步，所以门把它们和 skip 归为一类。

连续性门的判定更细，因为它有两层，降级路径不一样（`scripts/verify_continuity.py:53`）：

```python
def _classify(returncode: int, output: str, *, live: bool) -> str:
    counts = _counts(output)
    if returncode == 0:
        if counts["passed"] > 0 and not any(
            counts[name] for name in ("failed", "errors", "skipped", "xfailed", "xpassed")
        ):
            return "passed"
        if counts["passed"] == 0 and counts["skipped"] > 0:
            return "skipped"
        return "inconclusive" if live else "failed"
    lowered = output.lower()
    for status in ("provider_failure", "infrastructure_failure", "inconclusive", "skipped"):
        if status in lowered:
            return status
    return "failed"
```

关键在 `return "inconclusive" if live else "failed"` 这一行：同样是「退出码为零但结果不干净」，确定性层判 failed，live 层判 inconclusive。理由是「真实服务没跑成」和「我们的代码错了」不是同一件事，混成一个词就没法判断该修代码还是该修环境。函数最后一行同样有讲究：退出码非零、输出里又没有任何自述状态时，默认落到 failed 而不是 inconclusive。默认值放在对自己不利的那一侧。

同一套结果词表被三个门共用（连续性门、channel 门、turn 证据门），所以 V-R0 才能把不同门的结果排进同一个严重度顺序。turn 证据规范把这条原则单独写了一行：

> A verifier must not let one kind of result stand in for another.

同一套纪律在测试标记体系上也有体现。六个 opt-in 标记（real_llm、llm_judge、real_vm、real_channel、external_runtime、e2e）默认被保留套件排除，排除的方式是显式的：

```make
test-retained:
	uv run --frozen --all-extras --exact pytest tests -q --strict-markers \
	  -m 'not (real_llm or llm_judge or real_vm or real_channel or external_runtime or e2e)'
```

四个修饰词各有分工：`--frozen` 锁依赖版本，`--all-extras` 装齐保留的可选依赖，`--exact` 不留多余包，`--strict-markers` 让未注册的标记直接报错而不是静默当成无效过滤。最后一个最容易被低估：如果标记名打错一个字母，没有 `--strict-markers` 的话过滤条件会变成空操作，那些本该被排除的真实模型测试会被拉进来跑，或者本该被跑的测试被排除掉，而输出看不出任何异常。

测试文档里配了一句立场：这些排除是证据边界，不是豁免（The exclusions are evidence boundaries, not waivers），必需的门必须显式跑它对应的 live 层。

## 四、机制三：一个门的解剖

拿分发验证（V-P0）当样本，因为它最能说明「门」和「跑一遍测试」的区别。

先落地两个词：**wheel** 是装好即用的二进制分发包，`pip install` 拿到它直接解压就能用；**sdist** 是源码分发包，pip 拿到它要在用户机器上现场构建。两条路径产出的东西必须一致，否则「我测的那个包」和「用户装到的那个包」不是同一个东西。

V-P0 做九件事，每件对应一类事故（实现见 `scripts/verify_distribution.py`）：

1. **要求输出目录为空且在 checkout 之外**。防验证器把上次的产物当成这次的，也防它写脏源码树。
2. **给 HEAD、未提交 diff、未忽略的 untracked 文件和完整源清单一起做指纹**。报告绑的是这份指纹，不是「HEAD 一个人生产了这个包」。有未提交改动时报告记 `clean=false`，而不是把脏树当成 HEAD。
3. **只把 tracked 且未忽略的源拷进外部快照，拒绝指向清单之外的符号链接**。防本地临时文件、密钥、`node_modules` 被打进包。符号链接是绕开清单的经典路子，所以单独堵一次。
4. **所有子进程用白名单环境、隔离的 HOME 与缓存、空 PYTHONPATH**。防「在我机器上能装」。
5. **在快照里构建前端与 wheel、sdist**。真实 checkout 全程不动。
6. **校验路径安全、元数据、许可证、恰好一个前端 bundle、没有 node_modules 没有字节码**。历史上曾有 wheel 构建退出码为 0，却包含 2010 条 `node_modules` 路径，而对应 sdist 反而漏掉生成的 TUI bundle。
7. **把 base 加四个 channel extra 加 sandbox 装进六个互相隔离的环境**。防「装了全家桶才能跑」这类隐藏依赖。
8. **从 sdist 重建 wheel 并逐文件比对哈希**（只排除生成的 `RECORD`）。防两条分发路径产出不同的包。
9. **最后再确认一次源码在验证期间没有变过**。防边跑边改。

第 4 步的「白名单环境」不是形容词，是一个常量：

```python
_ENV_ALLOWLIST = {
    "COMSPEC", "LANG", "LC_ALL", "LC_CTYPE", "NIX_SSL_CERT_FILE",
    "PATH", "PATHEXT", "SSL_CERT_DIR", "SSL_CERT_FILE", "SYSTEMROOT",
    "TEMP", "TERM", "TMP", "TMPDIR", "WINDIR",
}
```

（原文一行一个元素，这里压行；`scripts/verify_distribution.py:122`。）名单只留语言环境、临时目录和证书路径，凡是不在名单里的宿主变量一律不传给子进程，然后再补一批指向隔离目录的值：

```python
env.update({
    "GIT_CONFIG_GLOBAL": os.devnull,
    "GIT_CONFIG_NOSYSTEM": "1",
    "HOME": str(home),
    "PIP_CONFIG_FILE": os.devnull,
    "UV_CACHE_DIR": str(cache_root / "uv"),
    "UV_NO_CONFIG": "1",
    "XDG_CONFIG_HOME": str(home / ".config"),
    "npm_config_cache": str(cache_root / "npm"),
    "PYTHONPATH": "",
    "PYTHONNOUSERSITE": "1",
})
```

把 git、pip、uv、npm 的全局配置全部指向空文件或临时目录，`PYTHONPATH` 清空，`PYTHONNOUSERSITE` 关掉用户级 site-packages。假象三里那次「继承了宿主凭证」的运行，就是这一段还没写全的时候跑出来的。

命令记录的设计值得单独讲。每条被拉起的子进程都记一条结构化记录：

```python
records.append({
    "command": command, "cwd": str(cwd), "exit_code": exit_code,
    "expected_exit_codes": list(expected), "accepted": accepted,
    "outcome": outcome, "elapsed_seconds": round(elapsed, 3),
    "log": str(log_path), "log_sha256": _sha256_file(log_path),
})
```

判定位是 `accepted` 而不是 `exit_code == 0`，`accepted` 的定义是 `completed.returncode in expected`。为什么需要这一层：六个环境各会跑一次未配置状态下的诊断命令，它的预期退出码就是 1，退出码为 0 反而说明装错了。

```python
doctor = _run(
    [str(executable), "doctor", "--json"],
    cwd=probe_cwd, env=probe_env, log_dir=log_dir, records=records,
    expected=(1,),
)
doctor_report = _validate_doctor_probe(doctor, probe_home / ".pico" / "config.json")
```

而 `_validate_doctor_probe` 还不止看退出码：

```python
if returncode != 1:
    raise VerificationError(f"unconfigured doctor probe must exit 1, got {returncode}")
...
if paths.get("config_path") != str(expected_config_path):
    raise VerificationError("doctor probe did not report the isolated Pico config path")
```

退出码只能证明「命令跑起来了」，最后这一行才能证明「它读的是这次隔离出来的配置路径，不是操作者真实的 home」。同一个断言顺手证明了第 4 步的隔离没有漏。

M4 那个「67 个命令探针」就是这么来的：六个环境的构建、安装、探针命令总数，每条都带预期值和接受判定，不是六十七个必须为零的返回码。同一次运行还会记下直接构建的 wheel 与从 sdist 重建的 wheel 各自的文件数与哈希（PR #42 那次是各 361 个文件、摘要相同）。这些数字随包内容变化，所以引用时必须带 PR 号：PR #37 那次是 47 条命令、358 个文件。

判定位应该是「预期与实际是否一致」，不是「返回值是否为零」。这条在任何验证脚本里都成立。

## 五、机制四：绑定 commit，以及一句值得背下来的话

发布候选门（V-R0）的规范文档把「为什么需要一个 driver 而不是一份清单」讲透了：

> What no single Gate can answer is the release question: did all of them pass, at the same commit, on the same machine, in one run. A checklist answers it by hand, and a hand-assembled release is exactly where evidence from an older branch, an older wheel, or an older PR gets reused because it looked green at the time.

driver 把十三层按依赖顺序跑一遍：`v_d0`、`v_t0`、`v_p0`、`host_gate`、`v_lp`、`v_c0_s0`、`v_lf`、`v_o0`、`v_te0`、`v_e0`、`deps_audit`、`assets`、`evolution`。这个顺序不是习惯，是数据依赖：V-P0 把验证过的 wheel 通过报告里的 `handoff.wheel` 字段交给主机门、V-LP 和真实进化运行层，而下游只有在 V-P0 的 `status` 是 `passed` 时才允许读这个字段。

它的绑定规则是拒绝而不是警告。driver 只读一次 `git rev-parse HEAD`，然后：

| 缺口名 | 什么时候记 |
|---|---|
| `report_stale_commit` | 子报告里记录的 commit 不等于本次运行的 commit |
| `report_stale_artifact` | 报告文件比声称产生它的那一层还旧 |
| `worktree_dirty` | 工作区有未提交改动 |
| `layer_not_run` | `--layers` 子集把这一层排除在外 |
| `live_provider_credentials_missing` / `feishu_credentials_missing` | 缺相应的凭证环境变量 |
| `distribution_handoff_missing` / `small_real_files_missing` | 上游没交出 wheel，或者小规模真实运行的输入文件不存在 |

`report_stale_artifact` 就是专门用来堵假象二那条时间线的：某一层跑失败、还没来得及写报告，于是继承了上一次的绿色文件。`worktree_dirty` 的理由写在规范里，一句话就够：发布证据描述的是一个 commit，脏树不是 commit。

缺口的严重度也分级，分法本身就是一次判断。缺凭证的 live 层判 failed，因为 harness 是能跑的，只差操作者的凭证；缺 V-P0 handoff、缺小规模真实运行输入的层判 inconclusive，因为什么都没测，也什么都没失败。

命令退出零但报告缺失、不可读、commit 对不上或产物过期的层，一律降级成 failed。规范里给了理由，这句话是整章最值得记住的：

> an unbindable pass is worth less than an honest failure

缺口机制还有一个细节：一层没跑不会被省略，会带着自己的状态和一个具名缺口出现在报告里。术语表专门写了 `_Avoid_` 条目：

> _Avoid_: "skip" -- a V-R0 layer that measured nothing is still reported with its own status and a gap, never omitted.

`--layers` 这个开发用的子集参数也照此办理：它写同一份报告，把没选到的层全部记成 `skipped` 加 `layer_not_run`，并且永远不可能报 passed。规范里补了一句 There is no flag that relaxes that，把「有没有后门」这个问题提前答掉了。

日常纪律的版本写在项目状态文档里，也是一句话：Counts below are tied to the named merged PR and must not be silently reused for a later release commit。这就是本教程口径表里每个数字都带「测于 PR #NN」的原因。

## 六、机制五：工件与索引分离

仓库只保存可评审的 schema、verifier、重跑命令和摘要。原始日志、构建包、探针环境与大型报告放在 Git 之外，并通过摘要和 digest 绑定到候选 commit。`scripts/check_large_files.py` 会拒绝大文件和不适合进入源码历史的二进制或网页资产。

作废的绿色结果和有诊断价值的失败都应保留在外部证据索引中，并明确标记处置状态。绿色只说明命令成功，只有来源、环境、候选绑定和 verifier 都成立时，结果才有资格支持产品结论。

## 七、机制六：CI 故意比验收小

先把「多小」说准。默认 CI（`.github/workflows/ci.yml`）三个 job：只对改动文件跑 pre-commit、七个文件的 Python lint 加四个文件的测试、完整的前端 lint 与 RPC 检查与类型检查与测试与构建。另一条 workflow（`commits.yml`）再跑三个 job：PR 标题与正文校验、commit message 校验、改动文件的大小与资产校验。六个 job 里没有一道验收门。

项目状态文档明写了这件事和它的边界：

> The default GitHub CI is intentionally smaller than release acceptance... It does not run the retained deterministic suite, V-P0, V-LP, V-LF, V-O0, or V-E0 on every PR.

开发门（`make ci`）也在测试文档里被明确标注为 development gate，不是完整验收。

为什么敢这么设计？因为门是按 issue 分派的：每个 issue 声明自己需要哪一道门，贡献者本地跑那一道并把结果绑进 PR。代价也认了，同一份文档的 P1 债务里写着：当前 CI 不强制完整验收模型，证据纪律依赖 issue 专属的本地与 PR 门。

三个「为什么不做 X」，答案都指向成本或口径：

- **为什么不在每个 PR 上跑全量？** V-P0 一次要构建前端、wheel 和 sdist，再装六个隔离环境；V-LP 与 V-LF 要真实凭证；V-O0 的 live 层要真的调 provider 和 embedding。挂到每个 PR 上，要么烧钱，要么把生产凭证放进 CI，两条都不接受。
- **为什么不给一个覆盖率数字？** 覆盖率答不了「哪个能力有证据」。donor 那次就是现成反例：四个文件的检查全绿，同期全量非模型套件 85 failed、12 errors。
- **为什么不定期刷新数字？** M4 的 67 条命令测于 PR #42，之后 #45 到 #47 都没重跑。散点刷新会产生一堆彼此不同 commit 的数字，看着新鲜实则不可合并。刷新的正确形式是在一个 commit 上把所有门一起跑，那正是 V-R0 的定义。

commit 规范是同一套思路的延伸。commit message 与 PR 正文都强制 ASCII，理由写在函数的 docstring 里而不是某份文档的叮嘱里（`scripts/commit_lint.py:45`）：

```python
def check_pr_body(body: str) -> LintResult:
    """The PR body becomes the squash commit body, so it must be ASCII-only.

    Only the ASCII rule applies (the body is free-form Markdown, not a
    Conventional-Commits header), so the header/subject checks are skipped.
    """
```

规则跟着它约束的对象走：因为 squash 合并会把 PR 正文原样搬成最终 commit body，所以 PR 正文要按 commit message 的标准校验，而且这条校验跑在 `commits.yml` 的 job 里，不是靠人记得。

## 八、真实翻车

**第一起：收缩公共表面之后，保留的契约断了。** PR #26 到 #36 连做减法（砍 WhatsApp 与它的 Bridge、砍其余九个 channel、砍媒体生成、砍远程技能市场、砍 deep research、拆 cron 与主动性、删 sentinel 与 heartbeat、收 CLI 与 TUI-RPC 公共面）。随后 PR #37 `fix: restore retained runtime contracts` 收拾残局，commit body 列了六条：

1. 会话历史变更在并发写者与存储失败下不再原子；
2. 终端前端的排队、重试、取消、粘贴、附件、切会话语义被破坏；
3. 持久化的运行时载荷未净化，子 agent 历史不再规范；
4. 调度器的终态 sink 失败未隔离；
5. 媒体输入校验把保留的附件投递一起砍了；
6. Pillow 升级，并删掉它那条已解决的例外条目。

发现方式比清单更值得讲：这些不是 CI 发现的，CI 那四个文件全绿。是 `make test-retained` 加前端全量套件跑出来的。改动比例也印证了它在补契约而不是加功能：测试增量接近产品代码的两倍。

数字线也从这里起步：保留套件 3015（PR #37）→ 3089（#42）→ 3121（#43）→ 3311（#47，教学基线，M1）→ 3567（#56，当前检查点，M19）。同一次 PR #37 的 V-P0 是 47 条命令、每个 wheel 358 个文件，到 PR #42 变成 67 条、361 个文件（M4、M17）。

**第二起：无证据的成熟度声明。** 飞书适配器曾在 `pico/channels/adapters/feishu/spec.py` 里声明 `maturity="live-gated"`，而当时没有任何一次 live 门通过。这个字段是单一数据源，驱动着 `channels list`、`channels status`、`doctor` 和引导流程的展示，于是四个展示面一起在夸大证据。修复的产品改动只有一行（`spec.py | 2 +-`，改回 `beta`），制度化的部分写进了规范：

> An adapter may declare `live-gated` only in the same change that records a passed live Gate run for a commit.

同一个修复还带了另一件事：常驻的 stderr 日志 sink 保留了 loguru 默认的 `diagnose=True`，任何一次 `logger.exception` 都会把失败帧的局部变量（入站消息体、发送者 id、令牌）打进终端。修法是把 `backtrace` 和 `diagnose` 都关掉，与文件 sink 对齐，并加一条终端回归测试；opt-in 的 `PICO_CLI_DEBUG` 镜像保留 loguru 默认值。两件事凑在一个提交里，主题是同一个：没有被检验的默认值会同时伤害可信度和安全。

## 九、这套纪律怎么反过来管住嘴

证据体系最实际的用途，是约束你怎么描述自己的工作。三条可以直接用的规则。

**能力声明必须带证据等级。** 「实现了记忆系统」是没有信息量的句子，它对一个能跑的 demo 和一套生产系统同样成立。有信息量的版本是：记忆的 Backend 协议与双轨实现有确定性覆盖，跨进程连续性有一项必需的 live 检查（M3），检索质量没有独立 benchmark。三句话，三个不同的等级，听的人立刻知道边界在哪，也知道下一个问题该问哪里。

**数字必须带 commit 与新鲜度。** 教学基线的 retained 3311 测于 PR #47（M1），当前检查点 3567 测于 PR #56（M19）；67 个分发命令是 PR #42 的历史计数，PR #50 后 V-P0 与 PR #54 fresh-wheel 消费不能沿用这个数字（M4）；TokenWise 的成本削减是 donor 期历史快照，且当时的驱动路径已经移除（M6）。被追问「为什么不刷新」时的标准答案：门是绑定 commit 的，散点刷新只会产生一堆不同 commit 的数字，完整刷新属于发布门的职责。

**没有的东西说没有。** 真实的进化运行没跑过，V-E0 全是 fixture（M2）；飞书有 harness 但没有一次通过记录；策略栈没有装配点（第 04 章）。这些在文档里都是显式条目，不是被动省略。面试里主动说出边界的人，比说「都做了」的人更难被问倒，因为最锋利的那个追问已经被你自己先问了一遍。

## 十、怎么被验证（这一章的自指部分）

门自己也被测试，而且用的是同一套办法：把测门的测试放进门自己的清单里，让门在跑自己的时候顺手证明自己还没坏。

- V-O0 的确定性层一共九个文件，第九个是 `tests/test_verify_continuity.py`，四个测试全在测 `_classify` 不放水：

```python
def test_mixed_pass_and_non_pass_cannot_pass_gate() -> None:
    assert _classify(0, "1 passed, 1 skipped in 0.01s", live=False) == "failed"
    assert _classify(0, "1 passed, 1 xpassed in 0.01s", live=True) == "inconclusive"
```

- V-C0 的契约清单里有 `tests/test_verify_channels.py`（10 个测试）和 `tests/test_verify_live_feishu.py`（8 个）；
- V-TE0 的检测器有 36 个测试，规范写明它们跑在损坏过的 fixture 上，而不是只跑一次健康运行；
- V-R0 的 45 个 driver 测试把所有子进程调用 monkeypatch 掉，只测选层、分类、commit 绑定、缺口聚合、状态和依赖对账这几个纯函数；它们跑在 `make test-retained` 里，也就是 V-R0 自己的 `v_d0` 层。

（测试数口径：`git show main:tests/test_verify_*.py | grep -c "^def test_"`，核实于 `b65f962`。）

turn 证据门还有一次自我修正，发生在 PR #51 落地之前的对抗评审里，commit body 把它列为 a verifier status-classification defect。原来的判定顺序是先看观测计数、再看发现项，于是「检测器发现了矛盾，但那类记录的计数器根本数不到」会被报成结果不确定。修完之后发现项优先于计数，注释写明了理由：

```python
# Findings outrank the observed count: a detector can contradict on records
# the unit counter never sees (a notice with no delivery span), and reporting
# that as inconclusive would sell a violated contract as an unexercised one.
if findings:
    status = FAILED
elif observed == 0:
    status = INCONCLUSIVE
else:
    status = PASSED
```

顺带记一个具体口径：连续性门只有三种结果，判定和退出码都在源码里写死：

```python
if deterministic_passed and live_passed:
    status = "passed"
elif deterministic_passed and args.live_mode == "off":
    status = "partial"
else:
    status = "failed"
...
if status == "passed":
    return 0
if status == "partial" and args.live_mode == "off":
    return 0
return 1
```

离线开发通道（`make verify-continuity-deterministic`）确实存在，退出码也确实是 0，方便本地迭代；但报告上永远写着 `status: partial`、`live_mode: off`。退出码可以对开发者宽容，报告不行。

## 十一、预演追问

**「你们的测试覆盖率是多少？」**
先换口径再回答。覆盖率这个单一数字回答不了「哪些能力有证据」，它只说哪几行被执行过。我们用的是分门的结构：保留的确定性套件三千多项测于某个具体 PR，另有连续性、进化、分发、真实 provider、channel 契约、turn 证据各自独立的门，每个门一条命令、一份带 schema 版本的报告，报告绑定 commit，报告里每层还挂着自己那份日志的 SHA-256。更重要的是证据等级不混用：确定性、契约、live、历史是四类等级，跳过、结果不确定、provider 失败、基础设施失败是结果状态不是等级，任何一个都不能满足必需门。这套区分是代码强制的，判定函数里 skip 和 xfail 都算不通过。

**「CI 全绿是不是就能发布？」**
不能，而且我们的 CI 是刻意比验收小的：默认 workflow 三个 job，只跑改动文件的 pre-commit、七个文件的 lint 加四个文件的测试、完整的前端检查，另一条 workflow 跑 commit 与 PR 正文的规范校验。理由是门按 issue 分派，谁改什么谁跑对应的门并把结果绑进 PR，这样才不用把真实 provider 凭证放进 CI，也不用每个 PR 都构建六个隔离环境。这么做的风险我们也写在债务清单里：纪律依赖人执行，所以最终需要一个把所有门收进一次运行的发布门，它现在已经存在了。有个反例可以佐证这个设计判断：上游基线时期那套小 CI 常年绿，同期全量非模型测试有 85 个失败、12 个错误。

**「怎么保证这次的绿色属于这次的代码？」**
三层，而且都是拒绝不是警告。第一，每份子报告记录自己绑定的 commit，与本次运行读到的 HEAD 不一致就记一个 `report_stale_commit` 缺口。第二，报告文件如果比声称产生它的那一层还旧，记 `report_stale_artifact`，这条专门堵「某层跑挂了没写报告，于是继承上次绿色文件」。第三，工作区有未提交改动直接记 `worktree_dirty`，因为发布证据描述的是一个 commit，脏树不是 commit。命令退出零但报告不可绑定的层会被降级成失败，规范里那句话我印象很深：一个无法绑定的通过，比一次诚实的失败更没价值。

**「你怎么知道你的验证脚本本身是对的？」**
两条。第一，门把测自己的测试放进自己的清单里。连续性门的确定性层九个文件里有一个是测它自己的分类函数，断言「一个通过加一个跳过在确定性层判失败」；发布门的驱动有 45 个测试，全部 monkeypatch 掉子进程只测纯函数，而这些测试跑在保留套件里，也就是发布门自己的第一层。turn 证据门的检测器还专门跑在损坏过的 fixture 上，不是只跑健康样本。第二，门自己翻过车并留了记录：turn 证据门原来先看计数再看发现项，「检测到契约违反但计数器数不到」会被报成结果不确定，评审时被抓出来改成发现项优先，注释里写了理由。能被自己抓到并修正的门，比声称完美的门可信。

**「你这个数字是在测模型，还是在测你的 harness？」**
分开答，这正是证据等级要解决的问题。V-E0 在教学基线是 301、当前检查点是 319（M20），两者都是 fixture 驱动，证明进化流程的生命周期、证据判定、候选清单校验、跨进程恢复和回滚产物成立，完全不调模型，所以测的是 harness，不能拿来当 benchmark 成绩。V-O0 的 live 层反过来，它必须真的调 provider 和 embedding 才算通过，测的是「真实依赖在场时这条路径通不通」。TokenWise 那组成本对比测的是缓存放置策略而不是模型能力，但它是 donor 期的历史快照，驱动路径后来被移除了，所以我只把它当历史证据引用。真实进化运行的效果数字现在仍没有，那一栏在文档里是空的。

**「一道门跑完，我能拿到手的是什么？」**
一个目录。以连续性门为例，`.pico/evidence/continuity/` 下有一份 `continuity-report.json` 和两份日志。报告里五个顶层字段：门名、状态、live 模式、schema 版本，加上 checks；checks 里每层记它跑的完整命令、pytest 的各项计数、日志文件名和那份日志的 SHA-256。所以你可以从结论一路反查到原始输出，也可以验证日志没被改过。报告里不会有 provider 密钥，也不会有异常消息原文，这是刻意的：证据要能贴进 issue，不能顺手泄露凭证。分发门的报告更厚一层，它带 handoff 字段把验证过的 wheel 路径交给下游的门。

**「这套东西不会太重了吗？」**
诚实答：对一个人的项目来说确实重，重的部分是写规范和写验证脚本，不是日常开发,日常只是跑一条 make 命令。收益有三处很具体。一是它让删代码变得安全，我们做过一轮大幅收缩，事后靠全量确定性套件发现打断了六条保留契约，CI 是发现不了的，那次修复的测试增量接近产品代码的两倍。二是它让数字可复用，简历上每个数字都能追到一条命令和一个 commit，被问「这是当前版本的吗」时有确定答案。三是它反过来管住表述，没有证据的能力声明在这套结构里根本写不出来，比如某个适配器曾自称已通过 live 门而实际没有，被发现后连带修掉了四个展示面的夸大。

## 口播稿

> 这个项目里我花了很多时间在证据体系上，核心是一条：能力声明必须能被检验。做法是把验证拆成一组有名字的门，确定性套件、跨进程连续性、分发、真实 provider、channel 契约、turn 证据关联、进化流程各一道，每道门一条命令、一份带 schema 版本的报告、一个明确的断言边界，报告里每层还挂着自己那份日志的哈希。关键区分有两个。第一，证据等级和结果状态是两回事，确定性、契约、live、历史是等级，跳过和结果不确定和外部失败是状态，后者永远不能满足必需门，这条是判定函数强制的，skip 和 xfail 都算不通过。第二，绿色必须能绑定到 commit，报告里记的 commit 对不上、报告比它那一层还旧、工作区是脏的，都会被记成具名缺口并把那一层降级成失败，规范里的原话是一个无法绑定的通过比一次诚实的失败更没价值。这套纪律的实际收益是它反过来管住了表述：我的每个数字都带着测于哪个 PR、之后有没有刷新；没有跑过真实运行的能力，我在文档里就写没跑过。

## 复习路径（10 分钟）
