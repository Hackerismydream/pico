# P00｜什么是 Agent Harness：从一条飞书消息认识 Pico

你在飞书里给 Pico 发了一句：

> 请查看这个仓库最近失败的测试，定位原因，并把结论发回这里。

过一会儿，聊天窗口里出现一条回复，里面写着失败位置、原因和建议。站在用户这一侧，整件事只有一句请求和一段结果，看起来像是模型读懂问题以后直接给出了答案。

可模型没有直接收到飞书事件，也没有亲自打开仓库、运行测试或把回复送回原来的会话。如果模型只负责生成下一步，这项任务中剩下的工作是谁完成的？

## 一次模型调用，只能给出下一步

最直接的方案很容易想到：

```text
收到文字
调用模型
把模型输出发回去
```

如果问题可以靠模型当前看到的信息一次回答完，这个方案已经够用。可“检查仓库里最近失败的测试”不是一道只靠文字推理就能完成的问题。答案取决于仓库此刻的代码和真实测试输出。

模型可以生成“读取这个文件”或“运行这条测试命令”的工具意图，但意图不会自动变成行动。必须有程序找到对应工具，检查这次调用是否允许，真正读取文件或启动命令，再把结果交还模型。

所以，一次模型调用的边界其实很窄：输入是当前信息，输出是文字或工具意图。它不会因为输出了一个 Tool Call，就自动拥有工具、工作区、对话顺序和结果交付。

## 工具结果回来以后，才出现连续的 Agent 行为

第一次模型调用只知道任务描述。工具真正运行以后，系统才得到仓库里的新事实：文件内容是什么，测试在哪里失败，刚才的修改有没有生效。

这些结果需要回到模型，下一步判断才有依据：

```text
模型判断 → 工具执行 → 返回真实结果 → 模型重新判断
```

模型可能继续读文件，也可能修改代码、重新运行测试，最后形成结论。判断、行动和反馈围绕同一个目标反复推进，直到产生结果或触发停止条件，这才表现为一次 Agent 运行。

这也是模型调用和 Agent 的根本区别：模型调用产生一次输出，Agent 则利用外部反馈持续推进一项任务。

不过，一个能够循环调用模型和工具的程序，仍然没有完成开头那条飞书任务。

## 一个能循环的 Agent，仍然不能独自完成飞书任务

把任务从聊天窗口送进循环，再把结果送回来，中间还有三段不能缺少的责任。

**接住任务。** 系统要识别消息来自哪里、属于哪段会话、谁发出了请求，以及最后应该回复到哪里。

**推进任务。** 系统要让模型判断、工具行动和行动结果持续衔接。任务运行期间如果又来一条消息，还要决定它是等待、影响当前任务，还是停止当前任务。

**结束任务。** 系统要保存已经发生的对话和结果，明确这项工作是正常结束、失败还是被取消，并把最终内容交给正确出口。

这三段责任覆盖了请求从进入系统到产生可见结果的完整路径。模型只参与“推进任务”中的下一步判断，其他责任不会因为接入了模型而自动出现。

> 配图说明：真实任务需要接住、推进和结束三段责任。原始飞书图片未纳入 Git 快照。

## 这层系统就是 Agent Harness

先把 Pico、Claude Code、Codex 这些名字拿掉。一个模型要在真实任务里连续工作，总得有程序做几件事：准备这次调用需要的信息，接住模型给出的工具意图，执行行动，把结果送回去，再决定要不要进入下一轮。少了任何一环，剩下的都只是孤立的模型调用。

这段循环是 Agent Harness 最省不掉的部分。模型处理不确定的信息，代码负责按规则执行，并留下足够的状态让下一步能够发生。这样的分工不是因为 Harness 比模型更聪明，而是执行工具、维护状态、决定何时停止，总得有程序来做。

内核之外，各家的画法并不一样。Anthropic 在 [Managed Agents](https://www.anthropic.com/engineering/managed-agents) 中把 Session、Harness 和 Sandbox 拆成可以独立替换的接口，Harness 只保留调用模型和路由工具的循环。OpenAI 介绍 [Codex Harness](https://openai.com/index/unlocking-the-codex-harness/) 时，则从完整产品体验出发，把 Thread 生命周期、持久化、认证、工具执行和扩展也算进来。两种说法没有冲突：前者在定义一套可替换的运行接口，后者在描述一套可以被多个客户端复用的 Agent 能力。

最近的论文也没有把 Harness 收束成一份标准清单。[《Architectural Design Decisions in AI Agent Harnesses》](https://arxiv.org/abs/2604.18071)调研了 70 个公开项目，最终仍把这个词当作“模型之外工程层”的简称；[《Code as Agent Harness》](https://arxiv.org/abs/2605.18747)进一步把代码看成连接推理、行动、环境和执行验证的运行载体。边界画在哪里，各家可以自己定。绕不开的始终是同一个问题：谁把模型的输出接到真实行动上，谁把行动结果送回来，让任务继续推进。

图里把这件事画成两层。内层就是刚才那段循环。系统进入真实产品以后，还会逐渐背上任务身份和顺序、权限、状态、记录与恢复、运行环境、结果交付这些责任，它们构成外圈；产品承诺不同，外圈也就不同。

> 配图说明：Agent Harness 的固定内核与弹性外圈。原始飞书图片未纳入 Git 快照。

<callout emoji="💡">
**在这套课程里，Agent Harness 是让模型判断能够在真实环境里持续推进的执行系统。**它接住任务，运行模型与工具之间的反馈循环，再把结果交还请求来源。
</callout>

模型、Agent 和 Harness 因此可以这样区分：

| 对象 | 它在任务中负责什么 |
|-|-|
| 模型 | 根据当前可见信息产生文字或工具意图 |
| Agent | 模型判断和真实行动围绕目标持续推进的过程 |
| Agent Harness | 让这个过程能够被接入、运行、约束、记录和交付的系统 |

Pico 就是一个具体的 Agent Harness。它采用了相对完整的边界：既包含模型与工具之间的反馈循环，也负责外部请求怎样进入、怎样获得运行边界、怎样留下对话记录，以及结果怎样交给出口。

## Pico 怎样把一条飞书请求带到结果

回到开头那条飞书消息。先不看类名，只按事情发生的顺序走一遍。

**消息进入。** 飞书适配器收到平台事件，完成去重、来源和内容检查，并保留会话地址。这个地址决定结果最后应该送到哪里。

**请求成形。** 不同平台的消息被整理成 Pico 统一理解的请求。一次入站请求会成为一个 Turn，也就是 Agent 对这条请求的完整反应。

**任务获得运行边界。** 同一段 conversation 中的 Turn 要保持因果顺序，也需要有取消边界；不同 conversation 可以各自推进。

**Agent 开始工作。** Agent Loop 准备当前信息，调用模型，执行工具，再把工具结果送回模型，直到产生最终内容或发生失败。

**对话留下记录。** 本轮用户消息、模型输出和工具交换进入 Session，使后续 Turn 能够知道这段对话已经发生过什么。

**结果回到原入口。** 最终内容进入投递路径，根据之前保存的来源找到飞书出口，再由 Channel 调用平台接口发送。

> 配图说明：一条飞书请求在 Pico 中的完整路径。原始飞书图片未纳入 Git 快照。

现在再把普通语言换成源码名，读者才有理由打开这些文件：

| 请求走到哪里 | 当前源码入口 | 先看什么 |
|-|-|-|
| 飞书事件进入 | `FeishuChannel._on_message` | 入口检查和回复地址 |
| 平台消息变成统一请求 | `Intake.publish` | `TurnRequest` 怎样携带来源与 conversation |
| 请求获得顺序和执行权 | `Lane` 与 `Scheduler` | 同一 conversation 的执行边界 |
| 模型与工具持续推进 | `AgentLoop.run_turn` | 最终内容怎样从统一事件出口产生 |
| 对话被保存 | `SessionManager` | Session 怎样保存一段有序对话 |
| 结果返回飞书 | `DeliveryHub` 与 `ChannelOutletAdapter` | 结果怎样按来源进入对应出口 |

## Agent 结束，不一定等于用户收到回复

一条真实请求有两个不同的完成时刻。

**运行结束**表示 Agent 不会再为这次请求产生新的行动。它可能已经形成答案，也可能失败或被取消。

**投递结束**表示结果已经经过出口，具体渠道的发送调用得到了结果。Agent 可以已经结束，但飞书发送仍然失败；投递失败也不会抹掉此前已经发生的模型调用和工具行动。

> 配图说明：Agent 运行结束与用户收到回复是两条线。原始飞书图片未纳入 Git 快照。

对当前飞书适配器来说，发送接口正常返回可以证明飞书接受了发送请求。聊天窗口是否已经显示、用户是否已经读过，仍然是更外层的事实。

这一区分让开头的任务真正闭环：模型生成答案只是中间结果，Pico 还要把这项工作收束并交给原来的会话。

## 总结

一次模型调用只能根据当前信息给出文字或工具意图；只有当工具结果重新进入下一轮判断，任务才形成持续推进的 Agent 行为。

Agent Harness 是支撑这段行为运行的工程系统。它负责接住外部请求，组织模型与工具之间的反馈循环，维护任务顺序和对话记录，并把最终结果交还请求来源。

Pico 就是一套具体的 Agent Harness。一条飞书消息进入 Pico 后，会依次经历请求接入、运行调度、Agent Loop、Session 记录和结果投递。模型负责判断下一步，Pico 负责让这些判断真正变成一次可以运行、约束、记录和交付的任务。

因此，Agent 产生最终答案只是运行结束；渠道完成发送，才进入投递完成。至于消息是否已经显示、用户是否读过，则属于更外层的平台事实。理解这几条边界，后面的章节就是在逐层拆开 Pico 怎样实现它们。
