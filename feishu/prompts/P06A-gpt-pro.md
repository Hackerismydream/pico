## 本章的第一性原理问题

整章围绕这一问推进：

> 过去发生过很多事情，系统为什么只让其中一小部分进入未来 Context？

```text

→ 为什么召回后仍要核对当前源码

```

### 二、一段经历怎样成为可用 Memory

讲清一条连续链路：

```text
原始经历
→ 候选解释
→ 写入许可
→ 带作用域与来源的记录
→ 更新或归并
→ 召回许可
→ 当前事实核验
```

重点解释：

- 用户明确要求、工具观察、第三方材料和模型推断为什么不能拥有相同证据等级；
- no-op 为什么是 Memory Writer 的正常能力；
- 写入许可与召回许可为什么控制不同风险；
- 为什么错误写入通常比漏记一条更危险；
- 归并为什么维护当前状态，而不是无限追加摘要；
- 召回相关不等于当前正确，容易漂移的内容仍要回到当前事实源核验。

### 五、沿一条 Turn 走完 Recall 与 Store

这是 Pico 部分的核心。完成一条正常链路，再讲异常：

```text
当前用户请求
→ Runtime 调用 Backend Recall
→ 获准的 Memory 进入 Context
→ Agent 使用当前 Tools 完成任务
→ Session 先保存本轮事实
→ Runtime 把可持久化消息交给 Backend Store
```

沿贯穿案例解释模型最终看到了什么，以及为什么它还需要读取当前源码确认今天的函数名和测试数字。

讲清 Session 先保存、Memory 后派生的意义：store 失败不能抹去已经发生的会话事实，也不能通过盲目重跑整个 Turn 修复。

不要在 happy path 中插入本地归并器、PicoBench、LoCoMo、安装错误或旧压缩路径。

### 六、失败边界与怎样判断 Memory 有用

只保留四种读者必须区分的状态：

| 状态 | 正确理解 |
|-|-|
| Recall 返回空结果 | 本轮没有获准使用的 Memory，任务可以继续 |
| Recall 或 Backend 启动失败 | Memory 产品路径发生故障，应显式暴露 |
| 操作者关闭 Memory | Session、Context 与 Skill 仍可独立工作 |
| Session 已保存但 Store 失败 | 会话事实存在，派生 Memory 未完成 |

评测只讲一个原则：Memory 是否有用，要看它是否改善最终任务行为、减少重复探索，并避免旧知识和跨作用域污染，而不是只看 Hit@k。
