# P92｜简历描述与证据边界

简历不是把模块名压成一串关键词。面试官真正会沿着四条线追问：为什么要做、你改了什么系统行为、对照方案是什么、数字怎样复现。下面给出可以直接使用的项目描述、不同篇幅的版本，以及每个数字的答辩边界。

## 使用前先确认一件事

这里的技术事实和实验数字都能从 Pico 的源码、冻结实验工件与当前 reducer 核对；但“由我设计”“由我实现”属于个人贡献归属，仓库不能替候选人证明。实际简历只保留自己确实负责、并能讲清设计取舍与代码细节的条目。

## 推荐标题与技术栈

**Pico：面向多轮复杂任务的 Agent Harness**

核心技术：Python、asyncio、Agent Runtime、Context Management、Session、Memory Plugin、Local Skill Retrieval、Tool Calling、MCP、Provider Routing、Agent Evaluation、Tracing / Observability

项目描述：面向 Agent 从单轮 Tool Loop 走向多入口、多会话和长任务后的工程问题，构建统一任务运行时，将会话级调度、上下文预算、持久 Session、可插拔 Memory、本地 Skills、Tool/MCP、消息投递和可复现实验收进同一套 Turn 契约与证据体系。

## 两条必须保留的核心描述

### 1. Scheduler、Lane 与独立并发池

> 针对多聊天渠道下长任务容易出现消息乱序、慢会话阻塞其他会话及后台任务争抢资源的问题，设计“同一会话按序、不同会话并行”的 Agent 任务调度器，并为用户请求和定时/子 Agent 任务分配独立并发额度；相较全局共享队列，前台 P95 排队时间降低 86.87%，后台满载时延迟放大由 2.05 倍降至 0.97 倍，并在 10,000 个请求中实现 0 丢失、0 重复执行、0 永久挂起。进一步通过 80 轮配对、4,160 次 DeepSeek 真实 Agent Turn 实验，将前台端到端 P95 从 13.57 秒降至 11.66 秒，中位数降低 13.53%（Bootstrap 95% CI：11.36%～15.26%）；4,160 个请求全部完成执行，任务 Verifier 通过率为 99.95%，Provider 失败、请求丢失和重复执行均为 0。

这段话里的两组实验必须分开理解：

- `86.87%`、`2.05x -> 0.97x` 与 `10,000` 次请求来自受控、本地、确定性的 Scheduler 配对实验，四个 Claim Gate 全部通过；
- `13.57s -> 11.66s` 来自真实 DeepSeek Agent Loop，4,160 个请求都执行完成，但任务 Verifier 是 `4,158/4,160`。因此可以报告测量结果与 `99.95%`，不能说“全部任务通过”或“正向 Claim Gate 全过”；
- 两次 Verifier 失败都是回复缺少唯一 marker，不是 Scheduler 丢请求，也不是 Provider failure；
- 两组 workload 都是为了制造 Head-of-Line 压力的实验，不是生产流量或线上 SLO。

### 2. TokenWise Provider-aware 缓存记账

> 针对多轮 Agent 重复传输系统指令、工具定义、历史消息和工具结果带来的输入成本，设计 TokenWise Provider-aware 缓存记账与成本评估机制，为 DeepSeek 原生前缀缓存统一记录命中/未命中 Token，并按模型专属价格重建调用成本；在 4 类固定任务场景、36 个配对区组（72 次 Trial）中，稳定请求前缀相较逐调用扰动反事实将保守缓存命中率从 0% 提升至 75.19%，单位验收成功任务的估算 API 成本从 \$0.008694 降至 \$0.002309，降低 73.44%，两组任务通过率均为 100%。

这段话必须同时保留四个限定：

- 缓存由 DeepSeek 原生提供；Pico 保持正常请求前缀稳定，并负责 hit/miss Token 归一化、价格重建和实验；
- 对照组每次故意扰动系统前缀与 Tool Schema，是实验反事实，不是可部署配置；
- 美元数是冻结价格表重建的估算成本，不是 Provider 发票；
- `75.19%` 与 `73.44%` 只对冻结的 4 类任务、36 个 Comparison Block、72 个 Trial、504 次 Provider call 成立。

## 一页简历的推荐四条版

如果版面只允许四条，优先保留下面这组。前两条放数字，后两条证明你不只会做 benchmark，也理解系统边界。

1. 针对多会话长任务的 Head-of-Line、消息顺序与前后台资源争抢，设计会话级 Lane 和 USER/SYSTEM 独立并发池；确定性配对实验中，前台 P95 排队时间相对全局 FIFO 降低 86.87%，后台满载延迟放大由 2.05x 降至 0.97x，10,000 个已接受请求实现 0 丢失、0 非预期重复执行、0 未决 Handle。
2. 构建 Provider-aware TokenWise 记账，归一化 DeepSeek 原生前缀缓存的 hit/miss Token，并按冻结模型价格重建成本；在 36 个配对区组、72 个 Trial 中，稳定前缀相较逐调用扰动反事实将保守命中率由 0% 提升至 75.19%，估算成本/验收成功任务由 \$0.008694 降至 \$0.002309，下降 73.44%，两组任务通过率均为 100%。
3. 构建统一 Turn Runtime，把 CLI、TUI 与 Gateway 收敛到同一 Runtime Assembly 和 Spine；通过 typed terminal events 区分正常完成、携带 Tool 失败的完成、Provider 失败、运行异常与用户取消，并将 Delivery 的 delivered/dropped/no_outlet 作为独立状态轴，避免用最终文本冒充任务结果。
4. 建立 PicoBench 证据闭环，冻结任务、模型、预算、Tool Catalog 与 Verifier，保留失败、重试、timeout 和原始 Trial 工件，再由 reducer 重建报告与 Claim Gate；在 Tool Disclosure 实验中识别出 Schema 估算 token 降低 93.45% 但任务通过数从 23/24 退化到 20/24，因而阻止只看 token 指标的策略上线。

## 偏 Agent Runtime 岗位的六条版

1. 以 `TurnRequest -> Scheduler -> Lane -> TurnRunner -> RuntimeEvent` 为统一执行协议，让 CLI、TUI RPC、聊天渠道、Cron 与 Subagent 共用一条 Runtime 主链；入口只做协议适配，Session、Memory、Tool 与 Provider 不在各 Host 重复装配。
2. 设计会话级 Lane、APPEND/INJECT/INTERRUPT 忙时策略与 USER/SYSTEM 独立并发池；Lane 成为 `TurnHandle` 的唯一 resolver，保证同会话有序、不同会话并行，并收束取消、自然完成与异常之间的竞态。
3. 构建多轮 Agent Loop，闭合 assistant tool call 与 tool result，统一 Tool Schema 校验、参数转换、timeout 和显式失败；将 Provider 错误分类、有限 retry/fallback、空响应恢复和最大迭代 Synthesis 纳入一条有上限的 Turn 生命周期。
4. 构建两阶段 Context Pipeline：先并行生成 Identity、Bootstrap、Memory 与 Skill 等固定 Segment，再在真实前缀、Tool Schema 和当前用户消息开销已知后选择历史；当模型辅助 Curator timeout、异常或给出无效计划时，回落到 protected/relevant/recent 的确定性 Fail-Safe。当前只报告机制与合同，不宣称未经完整 usage 证据支持的 token 优化幅度。
5. 将 Session、Memory 与 Skill 拆成三条状态路径：Session 维护有序对话与并发 fencing，Memory 通过外部 Plugin 合同 recall/store，Skill 通过本地 Catalog、BM25、Router 与 Resolver 完成候选发现和正文注入；三者只在 Context Engine 会合，不共享领域含义和持久化生命周期。
6. 建立 Trace、Session、Tool、Memory、Provider 与 Delivery 的关联语义，并用 PicoBench 将“跑完实验”“测量有效”“允许写正向结论”拆成三个 Gate；候选优化必须同时通过任务成功、usage 完整性、模型一致性与原始工件重建，失败不会被最后一次重试覆盖。

## 偏平台/基础设施岗位的三条版

1. 设计同会话串行、跨会话并行的 asyncio Lane Scheduler，并以独立 Semaphore 隔离用户与系统来源；确定性实验中 10,000 个请求 0 丢失、0 重复、0 未决，前台 P95 排队时间相对全局 FIFO 降低 86.87%。
2. 设计 Runtime Assembly 统一管理 Plugin、Session、AgentLoop 与可选 MemoryBackend 的构建和生命周期；显式区分 workspace 与 state，启动结果只解析一次，关闭阶段即使 Agent 清理异常仍继续回收后端。
3. 设计 Runtime Event 与 Delivery 解耦：每个 Outlet 使用独立有界串行队列、重试与丢弃终态，慢 Channel 不占住 Agent 执行 Lane；Turn 与 Delivery 通过 trace/conversation 关联但不互相改写。

## 偏评测/测开岗位的三条版

1. 建立 Agent 任务级评测合同，冻结 Task、Provider、Model、Budget、Tool Catalog、Retry 与 Verifier，保留每次 Trial、Provider failure、timeout 和 usage，不用“最终有一次成功”覆盖失败分布。
2. 从原始 artifact 重新计算配对样本、P95、bootstrap CI、cache hit rate、成本/verified success 与 Claim Gate，并以 plan digest、source SHA 和 report digest 约束报告身份；报告不可从汇总 JSON 自证。
3. 将任务通过率设为 token/成本优化的上位门槛：Tool Disclosure 虽将六个可测任务的可见 Schema 估算 token 降低 93.45%，但任务通过数由 23/24 降至 20/24，因此拒绝将其写成可上线正向优化。

## 不建议再放进当前 Pico 简历的表述

- 不把外部 Memory 后端的检索算法或未装配的多源融合写成 Pico 当前 Runtime 成绩。当前 Pico 能证明的是 Memory Plugin 合同，以及只装配 Local source 的 Skill 热路径。
- 不写“Context Curator 已证明节省多少 token”。当前对照实验只有 23/24 有效 Pair，usage 不完整，机制可以讲，正向效率数字不能讲。
- 不写“渐进式 Tool Disclosure 降低 93.45% token，优化成功”。必须同段写 23/24 到 20/24 的任务回退，结论是 Gate 拒绝上线。
- 不写“4,160 个真实 Agent 任务全部成功”。准确说法是 4,160 个请求全部执行，4,158 个通过 Verifier。
- 不写“Pico 实现了 DeepSeek KV Cache”。DeepSeek 实现缓存，Pico 做稳定前缀、记账、成本重建与实验。
- 不写“workspace 限制等于恶意代码沙箱”。路径约束、命令策略与 Sandbox transport 有边界，不应承诺强隔离。
- 不写“Evolver 会自动自我进化并上线”。候选处于隔离评测与 `pending_human`，人工激活与回滚工件是硬边界。

## 数字追问的逐字答法

### “86.87% 是怎么算的？”

> 我没有把所有请求混在一起重新算一个 percentile。实验按同一 workload 做七轮配对，每一轮分别跑全局 FIFO 和会话 Lane，计算前台 P95 排队时间的相对降幅，最后取七轮配对降幅的中位数，结果是 86.8747%，简历里保留两位小数。它是受控本地调度实验，不是生产 SLO。

### “为什么后台满载后反而是 0.97 倍，不是刚好 1？”

> 这个数是 loaded P95 除以 idle P95 的有限样本比值，不是理论常数。独立池下后台负载不占 USER semaphore，两个条件的前台分布只剩调度噪声，所以测到 0.9672。我的结论是“没有出现共享池那种 2.05 倍放大”，不会把 0.97 包装成后台负载能让前台变快。

### “10,000 个请求 0 丢失，能证明 exactly-once 吗？”

> 只能证明这组进程内 Scheduler 实验里，从请求被接受到 Handle 进入终态，没有丢失、非预期重复执行或永久未决。它不证明进程崩溃后的 exactly-once，也不证明 Tool 的外部副作用 exactly-once。跨进程持久化和外部幂等要看 Session、Cron claim 与具体 Tool 合同。

### “4,160 个 Turn 为什么没有通过正向 Gate？”

> 4,160 个请求都执行完成，Provider failure、请求丢失、重复执行和 runner exception 都是 0；但任务 Verifier 只通过 4,158 个。两个回复都缺少唯一 marker，其中一个触及 completion token 上限。预注册规则要求全部任务验证成功，所以 measurement 可以解释，positive claim 仍然 fail closed。我在简历里写 99.95%，不会写全部任务成功。

### “TokenWise 到底优化了什么？”

> DeepSeek 的缓存本来就存在，Pico 没有实现 Provider 侧 KV Cache。我做的是三件事：保持普通请求的稳定前缀；把 Provider 返回的 cache hit/miss Token 归一化；按冻结价格重建每次调用的估算成本。实验再用逐调用扰动前缀作为负对照，测稳定前缀带来的差异。

### “为什么用成本/verified success，而不是一次调用成本？”

> 因为只降低单次调用成本很容易通过让任务少做一步、甚至直接失败实现。成本/verified success 把所有有效 Trial 的成本放在分子，把通过任务 Verifier 的任务放在分母；失败任务的成本不会从分子删除。再加一条 treatment 任务成功率不能退化，成本优化才不会靠牺牲任务完成换来。

### “这些数字能外推到生产吗？”

> 不能直接外推。Scheduler 的确定性实验和真实 Agent 实验都使用冻结的 Head-of-Line workload；TokenWise 使用四类固定任务与一个固定 DeepSeek 模型。它们证明机制在这个实验合同下成立，并给出可复现的量级，不代表所有生产流量、模型或 Tool Catalog 都会得到相同结果。

## 最后一分钟检查

- 每个百分比能说出 baseline、treatment、样本单位和 reducer；
- “请求执行完成”“任务 Verifier 通过”“消息投递成功”没有混用；
- 估算成本没有写成账单，缓存没有写成 Pico 自研；
- current Runtime 没有装配的能力不写成默认开启；
- 个人贡献能指向自己真正修改过的文件、测试和设计决策；
- 面试官要求打开代码时，优先从 P02、P09、P10、P11 的源码锚点进入，而不是先展示汇总报告。
