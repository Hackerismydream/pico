# P91｜原始面经问题映射

## 0. 用法与口径

这份题表来自只读参考空间中的 19 份面经（其中 3 份由截图转录）以及 3 份集中问答材料。事实解释只以交付时 Pico 的 current `origin/main` 为准；参考空间没有被修改，也不作为当前实现的事实来源。

这里完整保留面试官原话，是为了不丢公司、轮次和追问语境。正式回答只使用 catalog 中的“当前措辞”或 occurrence 后的“当前改写”，不展开产品版本史。每个 canonical question 在 P90 都对应一份稳定回答骨架。

这里把两个概念刻意分开：

- **Occurrence**：原资料里实际出现的一条问题。即使同一句话在同一篇资料的提纲和答案标题里各出现一次，也保留两条 occurrence。
- **Canonical question**：语义相同或回答骨架相同的问题组。去重只发生在这一层，不会吞掉来源、公司、轮次或追问语境。

复合问题按原始条目保留为一个 occurrence，主问题决定 canonical group；需要时在备注里写次级 group。这样不会擅自改写原话，也能让逐字稿复用稳定回答骨架。

每个 occurrence 必须能追到下方 canonical catalog。Catalog 已给出该题的：当前措辞、Pico 模块、类型、考察点、回答证据锚点、诚实边界和建议深度。Occurrence 自身再标记原问题是否需要改写；两层合起来构成“每题至少一套元数据”。

### 状态标记

| 标记 | 含义 | 公开话术处理 |
|-|-|-|
| `A` | 当前 Pico 可直接回答 | 用当前术语和当前代码回答 |
| `R` | 原问题的术语、数字、模块数或装配前提与当前实现不一致 | 保留原话用于来源核对；正式话术只回答“当前改写” |
| `G` | 通用基础题或其他项目题 | 独立回答，不伪装成 Pico 实现 |
| `P` | 个人经历、个人用量、个人贡献或主观体验 | 必须由候选人补真实经历，仓库不能代答 |
| `E` | 竞品、公司产品或近期行业信息 | 发布前做当日外部核验；不能凭 Pico 仓库下结论 |

### 建议话术深度

| 深度 | 目标 |
|-|-|
| `S` | 核心直答；一句结论加一个边界 |
| `M` | 标准展开；结论、机制、失败路径、一个代码锚点 |
| `D` | 白板深挖；完整时序、不变量、反例、证据和未证明部分 |

## 2. 诚实边界字典

| Boundary | 必须保留的边界 |
|-|-|
| `B01` | 有代码和合同不等于有真实模型效果或生产稳定性证明。 |
| `B02` | 受控 benchmark 不能外推为生产 SLO、普遍成功率或所有任务表现。 |

## 5. 逐字稿作者的映射规则

1. P90 先按 canonical question 写稳定回答，再把各 occurrence 的公司/轮次语境做开场调整；不要为同义题复制出互相矛盾的数字。

3. `P` 题必须留下候选人填空位，例如真实开发时长、日均 Token、个人踩坑和个人贡献。仓库事实不能冒充个人经历。
4. `E` 题发布前需要实时核验。即使外部信息查不到，也要明确说“不根据猜测回答竞品内部实现”。
5. `G` 题保留在完整题库，但与 Pico 章节分栏。算法、网络、数据库、RL 或其他仓储项目不能硬映射为 Pico 成果。
6. 任何指标回答都先说 workload/baseline，再说样本数和结果，最后说 Verifier 与 Claim Gate；不得只报一个百分比。
7. 讲 Scheduler 时必须拆开 deterministic 10,000-request 实验和 4,160 次真实 DeepSeek Turn 实验；后一组必须同段说 4,158/4,160 Verifier、`positive_claim_eligible=false`。
8. 讲 TokenWise 时必须同时说 DeepSeek 原生缓存、逐调用扰动反事实、冻结 4 类 workload、估算成本/verified success 和两臂 100% task pass。
9. 讲 Context 时只讲两阶段 Pipeline、快/慢/保底路径和无效对照实验，不使用 12 组、字符比例或 16.19% 作为当前事实。
10. 讲 Memory/Skill 时坚持 `B10/B14`：Pico 定义 Memory Plugin 合同，Skill 当前走 Local BM25；不把外部后端内部或未绑定当前源码的指标说成 current main 成绩。
