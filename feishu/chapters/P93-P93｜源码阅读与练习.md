# P93｜源码阅读与练习

这份练习不要求先把整个仓库读完。每次只沿一条职责链进入，先写下预测，再读实现与测试，最后用一个可观察结果推翻或确认预测。不要用“测试过了”代替结论；验收时要能指出哪个对象拥有状态、哪个分支产生终态、失败后谁继续清理。

## 练习环境

- 源码：Pico 当前 `origin/main`；
- 运行测试统一使用 `uv run pytest ...`；
- 不触发真实 Provider、付费 campaign、真实聊天平台或外部副作用，除非练习明确要求且已单独授权；
- 修改前先建立自己的分支或临时 worktree，不在他人的活动分支上实验；
- 每个练习保留一页实验记录：假设、入口、观察、结论、没证明什么。

## E00｜画出一条 Turn 的所有权链

目标：不看课程图，自己从入口走到 Delivery。

阅读顺序：

1. `pico/spine/turn.py`
2. `pico/spine/runner.py`
3. `pico/agent/spine_runner.py`
4. `pico/spine/scheduler.py`
5. `pico/spine/events.py`
6. `pico/spine/delivery.py`

提交物：一张只包含对象和箭头的图，并在每条箭头旁写出数据类型。至少回答：

- `TurnRequest` 在哪里第一次出现；
- `TurnOutcome` 由谁返回；
- terminal event 由谁发出；
- `Text` 什么时候才成为 Delivery 的输入；
- 哪个对象是 `TurnHandle` 的唯一 resolver。

验收：图中不得把 Agent Loop 直接连到具体 Feishu API，不得把 Delivery failure 画成 Turn failure。

## E01｜证明三个 Host 用的是同一套装配规则

目标：区分“仓库里存在能力”和“Host 已装配能力”。

阅读：

- `pico/cli/_runtime_assembly.py`
- `pico/cli/_runtime_host.py`
- `pico/cli/commands.py`
- `pico/cli/gateway_commands.py`
- `pico/tui_rpc/server.py`
- `tests/test_runtime_host_contracts.py`

任务：列出 CLI once、TUI、Gateway 各自怎样拿到 `RuntimeAssembly`，再做一张能力表：Session、MemoryBackend、Plugin Tools、Token Strategies、Router 分别是“构造”“传入”“可选”“未装配”中的哪一种。

验收：必须指出 `workspace` 与 `state` 分别流向哪里；不能因为 `_token_wise_stack.py` 存在就写共享 Host 已启用策略。

## E02｜实现一个最小 fake runner，观察 Lane 语义

目标：亲手看到“同会话按序、不同会话并行”。

任务：在临时测试中实现一个可控 `TurnRunner`，为每次调用记录 start/end 时间，并用 `asyncio.Event` 控制释放。提交：

- conversation A 连续提交两个 Turn；
- conversation B 提交一个 Turn；
- 在 A1 未释放时证明 B1 可以开始而 A2 不能开始；
- 释放 A1 后证明 A2 才开始。

参考：`tests/test_spine_scheduler.py`。

验收：不要使用 `sleep` 猜时序；用 Event 和明确断言建立 happens-before。

## E03｜构造 INJECT 错过 drain 的边界

目标：理解“要么 drain，要么重新排队”为什么需要明确所有权。

任务：阅读 `Lane.submit()` 与注入 drain 逻辑，写一段事件时间线，覆盖：

1. 当前 Turn 仍在模型迭代；
2. 新消息以 INJECT 到达；
3. 当前 Turn 已越过最后一个 drain 点；
4. 消息没有被消费；
5. Lane 把它重新变成后续工作。

验收：说明如果没有第 5 步，消息会处于哪种“无人拥有”状态；再指出哪个测试冻结了该语义。

## E04｜追一轮 Tool Call closure

目标：理解为什么 assistant tool call 与 tool result 不能被随意裁开。

从 `AgentLoop` 的模型调用进入 Tool Registry，记录下列对象的实际形状：

- Provider 返回的 tool call；
- 参数转换与 JSON Schema 校验；
- `ToolResult`；
- 写回 messages 的 assistant/tool 对；
- 下一次 Provider 调用看到的闭合历史。

故障注入：让 Tool 返回 `failed=True`，观察为什么 Turn 仍可能形成最终 Text。

验收：能准确区分 `ToolResult.failed`、`completed_with_tool_failure` 与 `TurnFailed`。

## E05｜给 Provider 恢复预算做状态表

目标：不把 retry、fallback、Context 收缩和 Synthesis 混成一个“重试”。

阅读：

- `pico/providers/base.py`
- `pico/agent/loop/recovery.py`
- `pico/agent/loop/main.py` 中模型调用与最大迭代分支

任务：为 timeout、rate limit、context length、empty response、未知异常、最大迭代耗尽分别写：是否 retry、是否换模型、是否缩 Context、预算在哪里扣、最后映射成什么结果。

验收：必须注明当前 retry/fallback ladder 覆盖哪些调用路径，不能把非流式机制自动外推到所有流式分支。

## E06｜手算一个 Context Budget

目标：理解两阶段装配为什么不是“把六段 concat 一下”。

给定一个虚构预算，列出 Identity、Bootstrap、Memory、always-on Skill、候选 Skill、Tool Schema、历史和当前 user 的 token 估算。先预测 Phase A 固定多少预算，再计算 Curator 可用历史预算。

随后阅读：

- `pico/context_engine/assembler.py`
- `pico/memory_engine/base.py`
- `pico/context_engine/segments/curator.py`
- `pico/context_engine/curator.py`
- `pico/context_engine/history_trimmer.py`

验收：写出三条路径的触发条件：完整历史直通、模型辅助选择、确定性 Fail-Safe；再说明 Tool Schema 为什么虽然不在 messages 内，仍必须计入预算。

## E07｜制造一个 Curator 无效计划

目标：看到 Fail-Safe 是真实控制流，不是文档口号。

任务：用 fake Curator 返回包含越界索引、重复索引或破坏 Tool closure 的计划，观察 validator 怎样拒绝，再验证 fallback 保留 protected、relevant、recent。

验收：最终 messages 必须恰好一个 system、一个当前 user，Tool closure 合法且不超预算。记录 invalid plan 没有被静默当成成功。

## E08｜区分四种“恢复”

目标：避免把 Session、workspace 与导出混成 Memory。

分别完成：

1. Session resume；
2. undo 最后一轮；
3. fork 出新会话；
4. Portable Session Export 并离线校验。

再阅读 `pico/agent/loop/checkpoint.py`，写出 Checkpoint 的前置 policy、commit 时机、Interrupted Turn 的恢复提示来源和当前没有提供的能力。

验收：不能说 Checkpoint 自动 rollback workspace；必须说明硬退出或取消发生在 Agent Loop 收尾前时，当前 Turn snapshot 可能不存在。

## E09｜让并发 Session writer 发生冲突

目标：理解进程内锁和跨进程 fencing 的差别。

阅读 `pico/session/manager.py` 的 load、append、rewrite、undo、fork 路径与对应测试。构造两个 writer 读取同一 generation 后分别尝试改写。

验收：说明哪个操作只追加，哪个操作重写历史，generation 怎样阻止后写者覆盖先写者；不要把 JSONL 文件存在当成并发安全证明。

## E10｜画出 Memory 与 Skill 的两条召回链

目标：证明二者只在 Context 会合，不能共享领域含义。

Memory 链至少包括：query、`MemoryBackend.recall()`、不可信文本边界、Memory Segment、after-turn store。

Skill 链至少包括：Local catalog、BM25 candidate、Router、Resolver、always-on / candidate admission、完整正文或引用。

验收：标出当前 Runtime 实际装配的 Skill source；不得画当前未启用的远程 marketplace、生产语义检索或多源 RRF 成绩。

## E11｜新增一个最小 Tool

目标：完整走过 Tool Contract，而不是只写一个 async 函数。

实现一个无副作用的教学 Tool，至少覆盖：

- 唯一 name 与 description；
- 参数 dataclass / Schema；
- 字符串到目标类型的转换；
- 缺失参数、额外参数和类型错误；
- timeout；
- 正常 `ToolResult` 与 `failed=True`；
- Registry 重名拒绝。

验收：测试文件遵守仓库命名规则；错误必须在 Tool 边界变成可定位结果，不能让模型看到未处理 Python traceback。

## E12｜验证 MCP 不是另一套 Agent Loop

目标：理解 MCP 是 Tool provider/transport，而不是并行的任务运行时。

启动一个真实本地 MCP transport，注册一个只读工具，观察它怎样被包装并进入同一 `ToolRegistry`。记录连接、schema discovery、调用、timeout、关闭与 transport failure。

验收：指出 MCP 工具与内置 Tool 进入模型后的共同合同，以及 secret、远端信任和宿主执行边界仍然由谁负责。

## E13｜用一条 Trace 重建真实结果

目标：从证据回答“哪里成功、哪里失败”。

构造或选取一个“Tool 失败但 Agent 给出最终回复，Delivery 又失败”的确定性场景，按 trace id 找出：

- `spine.turn`；
- `session.turn`；
- 每个 `llm.call`；
- `tool.call` 与 failed 属性；
- usage 行；
- Turn terminal；
- `channel.deliver` 与 Delivery outcome。

验收：最终结论必须写成两条轴，例如 `completed_with_tool_failure + dropped`，不能只写 success/failure。

## E14｜从 raw Trial 重建一个 Claim

目标：理解报告为什么不能自证。

选择不触发 Provider 的 PicoBench fixture，完成：

1. 核对 source SHA、plan digest 与任务身份；
2. 从 raw Trial 读取 terminal、usage、Verifier；
3. 运行 reducer；
4. 比较 report digest；
5. 分别判断 `ship_complete`、`measurement_valid`、`positive_claim_eligible`。

验收：人为删除一条 usage 或制造 task failure，观察哪个 Gate 失败；不能手改 summary 让结论重新变绿。

## E15｜解释一个“指标变好但不能上线”的实验

目标：练习工程判断，而不只会报正数。

使用 Tool Disclosure 结果：可见 Schema 估算 token 降低 93.4513%，但任务通过数从 23/24 变成 20/24。写一页上线评审：

- primary task metric；
- secondary efficiency metric；
- gate；
- finding；
- 是否上线；
- 下一轮最小实验。

验收：结论必须是当前 treatment 未获正向资格，而不是“优化 93.45%”。

## E16｜审一遍 Evolver 的权限边界

目标：判断“候选通过”与“运行环境被改变”之间还有多少步。

沿着 Candidate Manifest、allowed files、隔离 apply、screen、confirm、sealed test、Activation Record、Rollback Artifact 阅读。用一张状态机表示从 candidate 到 `pending_human`，并标出人工操作点。

验收：说明哪些 Candidate Label 当前有真实 evaluator，哪些会 fail closed；不能把 `accepted`、`activated` 字段写成自动修改 checkout 或自动发布。

## 综合作业｜从故障到证据闭环

选择一个不触发真实 Provider 的故障，例如：

- 同会话 INJECT 错过 drain；
- Tool timeout 后 Agent 仍需收束；
- Delivery 重试耗尽；
- Curator 给出无效计划；
- Session rewrite generation 冲突。

完整提交：

1. 故障场景与影响边界；
2. 负责模块与不负责模块；
3. 最小可复现测试；
4. 预期 Runtime Event / terminal / trace；
5. 修复或解释；
6. 回归测试；
7. 不能由这次实验证明的结论；
8. 一段 90 秒面试答法。

验收标准不是代码量，而是所有权清晰、失败可重现、结论能从工件重建。
